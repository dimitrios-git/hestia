# Tool configurations

Per-tool config details for this dotfiles repo — split out of `CLAUDE.md` (2026-08-18) to keep that file within its size budget. See `CLAUDE.md` for repo-wide architecture, the symlink/render conventions, secrets/signing, and the bootstrap system; this file is the per-app reference it points to.

### Vim (`user/vim/.vimrc`)
Uses **vim-plug** for plugins. To install plug.vim on a fresh system:
```sh
curl -fLo ~/.vim/autoload/plug.vim --create-dirs \
     https://raw.githubusercontent.com/junegunn/vim-plug/master/plug.vim
```
Then open Vim and run `:PlugInstall`. CoC extensions install automatically via `g:coc_global_extensions`. The config targets both Vim and Neovim — some plugins are conditional on `has('nvim')`.

Key plugins: `coc.nvim` (LSP/completion), `ctrlp.vim` (fuzzy finder), `vim-fugitive` (git), `copilot.vim` (requires Vim ≥ 9.0.0185), NERDTree, `vim-devicons` (Nerd Font filetype/folder glyphs in NERDTree/CtrlP). Theme: the `hestia` colorscheme (`user/vim/colors/hestia.vim`, GENERATED from `palette.yml` by `render.py` — self-contained, no longer a `wildcharm` wrapper); in the `theme_variant` the symlinked `~/.vim/hestia-background.vim` selector sets (`set background=dark|light`, sourced by `.vimrc` before `colo hestia`; falls back dark). **`vim-devicons` must be the last `Plug`** (it patches the plugins it decorates at load time) and needs `set encoding=UTF-8` + a Nerd Font in the terminal (we have both — Lilex Nerd Font via kitty). Icon colours mirror the GTK file manager: **folders hestia violet `#7c3aed`, other icons coloured per file extension from the hestia syntax palette (via `vim-nerdtree-syntax-highlight`), unknown ones neutral grey** (`#9e9e9e` on dark / `#626262` on light — per `&background`; icon only, names keep their normal colour). devicons injects the glyph into NERDTree's `[…]` flag region, so all icons inherit **`NERDTreeFlags`** (which links to `Number` → a hestia red — the source of the stray red on file icons); the `FileType nerdtree` autocmd `s:HestiaNerdTreeIcons` recolours `NERDTreeFlags` to grey (`ctermfg=247`) for the default, then a syntax match (`hestiaDevIconFolder`, built from devicons' own folder-symbol vars — no hardcoded codepoint) overrides the folder glyph to violet (`ctermfg=99`, wins via `containedin=ALL`). cterm cells are exact, so colours hold with or without `termguicolors`. NERDTree colours via highlight groups, **not** `LS_COLORS`/dircolors. Colour-by-filetype is provided by **`vim-nerdtree-syntax-highlight`** (loaded before vim-devicons), with per-extension colours set from the hestia syntax palette (`g:NERDTreeExtensionHighlightColor`, per `theme_variant`). The statusline is white-on-violet accent (`set laststatus=2` so it's always shown).

**Markdown viewing** — three layers:
- `:Glow` (or `<leader>md` = `\md`, markdown buffers only) renders the current file in **glow** as a full-screen pager in the **same terminal** (suspends Vim until `q`, like vifm), via `:!glow -p %`. Works in **both Vim and Neovim** — this is the plain-Vim path. Calls `GlowPreview()`; glow gets a real TTY so theming comes from `~/.config/glow/glow.yml` (see Glow section).
- `render-markdown.nvim` — live **in-buffer** rendering, **Neovim only** (needs treesitter/Lua, absent in plain Vim). Set up in a `has('nvim')` Lua block; headings themed to `#7c3aed`. Dormant until `:PlugInstall`.
- `markdown-preview.nvim` — browser-tab live preview, **Neovim only**; kept as the escape hatch for diagrams/math.

### Neovim (`user/nvim/init.vim`, `user/nvim/lua/trees.lua`)
Neovim **shares the Vim config** rather than duplicating it. `init.vim` prepends `~/.vim` to `runtimepath` (so `plug.vim` in `~/.vim/autoload` and plugins in `~/.vim/plugged` are reused) and then `source`s `~/.vimrc`. The `has('nvim')` branches in `.vimrc` then activate the Neovim-only plugins (`render-markdown.nvim`, `markdown-preview.nvim`) and `lua require('trees')` (treesitter config in `user/nvim/lua/trees.lua`).

Fresh-install steps (Debian trixie ships **0.10.4**, recent enough — `apt install neovim`, package is `neovim`, binary is `nvim`):
1. `nvim` → `:PlugInstall` (fetches the nvim-only plugins into the shared `~/.vim/plugged`; `markdown-preview.nvim` runs `npm install`, so Node/NVM must be loaded).
2. Treesitter parsers compile on first run — needs a **C compiler** (`gcc`). `:TSUpdate` if any fail.
3. Open a `.md` file: `render-markdown.nvim` renders in-buffer (headings themed `#7c3aed`); `:Glow` still works as the shared full-screen pager.

### Bash (`user/bash/.bashrc`)
- Vi mode (`set -o vi`); git-aware prompt (cwd, branch, staged/unstaged/untracked counts, exit-status colour). The prompt is **identity-adaptive** from one shared rc: a normal login user gets `path branch $` (no username), but **root** prepends a **red** `\u` and the **`claude`** agent an **orange** (`38;5;208`) `\u` → `user path branch $`. Same file, coloured by `$EUID`/`$USER` — so `sudo su` shows red because **root sources this same `.bashrc`**, not the caller's (a "go red when root" test in the *caller's* prompt never fires once you're elevated). Needs the rc deployed where it's sourced: the `dotfiles` role symlinks it into dimitrios's home, and — since the **claude-environment-parity pass** (below) — into **`claude`'s** home too (which retired the old manual stopgap symlink). `/root/.bashrc` only goes red once the rc reaches root (a manual/optional `ln -s` — root's home isn't managed yet).
- Loads **NVM** on startup. Sets `GPG_TTY=$(tty)` (needed for terminal GPG signing), exports `EDITOR`/`VISUAL=vim`, and prepends `~/.local/bin` to `PATH` (guarded against duplicate entries). (The system-wide `editor` **alternative** is also pointed at `vim.basic` by the `packages` role — Debian defaults it to nano; git uses `core.editor=vim` regardless.)
- **`gpg-unlock`** function: caches the GPG signing passphrase for the session (prompts once via pinentry-tty), so a cold cache stops failing harness commits. Reads the key from git config; refuses to run under `$CLAUDECODE`. See the signing section.
- **SSH agent:** exports `SSH_AUTH_SOCK="$XDG_RUNTIME_DIR/openssh_agent"`. The agent itself is **Debian's shipped socket-activated user unit** (`/usr/lib/systemd/user/ssh-agent.socket`, already `enable`d — auto-starts on login); we deliberately use that rather than a custom unit. greetd doesn't source `.bashrc`, so this export covers interactive shells (terminals, Ansible). The SSH key is now **auto-loaded at login** by the credential-unlock hook (see the signing section), reading the passphrase from the gnome-keyring login keyring — so no per-boot `ssh-add`. It persists the whole session. (Fallback if the hook ever doesn't run: `ssh-add ~/.ssh/<your key>`, i.e. the `ssh_key_file` host_var.)
- **ssh TERM fix:** under either hestia terminal (`TERM=xterm-kitty` or `TERM=alacritty`), `ssh` is aliased to advertise `TERM=xterm-256color` — servers rarely have either terminfo entry, so without this backspace/arrows garble on remote shells. Plain `ssh` keeps working keys **and** the server's login MOTD; use `kitty +kitten ssh <host>` explicitly for full kitty integration remotely (it installs the terminfo but bootstraps via a command, so it skips the MOTD — kitty-only, Alacritty has no equivalent kitten).
- Sources **`~/.bash_secrets`** for secrets (see above).
- No Rust: a previous `curl … | sh` rustup auto-installer block was removed (it could silently reinstall on shell startup). Install toolchains explicitly, never from `.bashrc`.

### Vifm (`user/vifm/vifmrc`)
Wayland-first file manager. The colorscheme is the **GENERATED** `colors/hestia-{dark,light}.vifm` pair (render.py, M7 PR2; the bootstrap symlinks the `theme_variant` one to `colors/hestia.vifm`, so vifmrc's `colorscheme hestia` is variant-blind; on light the common file-type groups drop from the bright to the base ANSI slots for readability). Images → `imv-wayland`, video → `mpv`, PDFs → `zathura`, office docs → `libreoffice`, **Markdown** → **glow** (`:file` offers "Edit in vim"). **Audio** opens in **cmus** (`cmus-remote -f`, play-now) and falls back to `mpv --no-video` when cmus isn't running; `:file` offers queue / mpv alternatives. Preview pane (`w`, on by default) uses `bat` (code, hestia theme) / `mediainfo` (media + image info) / `pdftotext` (PDF) / `glow` (markdown); images are info-only in the pane and open in `imv` (in-pane rendering tried twice — kitty graphics, then viu half-blocks — and dropped both times; the block mosaic wasn't worth the info text); **directories preview as a coloured `tree -C -L 2`** (LS_COLORS — so it matches `ls` and vifm's own file-type colours by construction; `.git` pruned; flat-`ls` fallback if tree is absent). Since 2026-07 (ranger/yazi-inspired, from the file-manager evaluation) the browsing pane uses **miller columns** — `set milleroptions=lsize:1,csize:2,rsize:0` + `set millerview` — a slim parent-context column left of the file list, so with quick view on the layout reads as the ranger triple *parent | current | preview*; `rsize:0` keeps miller's own in-pane preview column off (the quick-view pane already previews everything, dirs included). Clipboard yank (`yd`/`yf`) uses `wl-copy`. Comment syntax is `"` (vim-style).

**Git branch-vs-main helpers** (four commands, base auto-detected main→master, all in `vifmrc`; the pipeline-bearing two share `user/vifm/scripts/git-changed.sh`): `:gd` diffs the **cursor file** vs the branch base in vimdiff; **`:gc`** (key `gc`) opens a **custom-view jump list** of exactly the files this branch changed (Enter opens); **`:gs`** (key `gs`) **highlights** those files *and the folders leading to them* inline in the normal browser via `:select`; **`:gr`** (key `gr`) `cd`s to the **repo root** — handy on its own and the tidy way out of the `:gc` list (or the built-in **`gh`** key / its **`:gh`** alias returns to where you opened it). The `:gd`/`:gc`/`:gs` take an optional base ref like `:gd origin/main`. Several vifm constraints shaped these: a `|` in a `:command`/`:select` is parsed as a command separator (so the pipeline is in the script, not inline); vifm clears the pane selection on directory load (so **auto-highlight via `autocmd DirEnter` doesn't stick** — the `gs` key is the one-press substitute; note `:gs` reuses the selection that file ops like `dd`/`yy` act on); a macro wrapped in single quotes is **not** expanded (so `:gd` uses bare `%c:p`); vifm 0.14 has no `trim()`/`substitute()` (so `:gr` strips `system()`'s trailing newline in-shell with `tr -d`, `|| echo .` making it a no-op outside a repo instead of jumping to `$HOME`); and `gh` is a built-in **key**, not a command, so `:gh` is a `command! gh :normal! gh` alias (typing `:gh` otherwise gave "Invalid command name"). `:gd` resolves the cursor file by **full path → repo-relative** and runs git with `git -C`, so it works from a normal listing *and* the `:gc` custom view (a cwd+basename version showed blank panes there). The catch-all `fileviewer` passes **`%c:p`** (not `%f`): on the `..` parent entry `%f` expands to nothing, shifting a pane dimension into `preview.sh`'s `$1` (the old `cannot open '48'`); `%c:p` is always one absolute path, so `..` previews the parent listing.

The markdown **preview-pane** call is `CLICOLOR_FORCE=1 glow -s ~/.config/glow/hestia.json -w %pw`: when piped (the preview pane is notty) glow drops colour **and** emits malformed empty-param SGR (`ESC[;;1m`) for bold, which vifm's ANSI parser can't read and leaks as literal `1m` in the pane. **`-s` does NOT force colour** (it only carries the style's bold); **`CLICOLOR_FORCE=1` does** — it makes glow emit well-formed SGR (like `bat --color=always`) that vifm renders cleanly. Caveat: forced notty output is **16-colour** (no truecolor), an approximation of the hestia hex; `-s` keeps that mapping on-theme. The full-screen **open** action (`glow -p`) runs in a real TTY, so it gets truecolor and the default style from `glow.yml`.

### Glow (`user/glow/glow.yml.j2`, `user/glow/hestia-{dark,light}.json`)
Terminal Markdown renderer (apt: `glow`). Used by Vim (`:Glow`/`<leader>md`) and vifm (open + preview).
- `glow.yml` sets the default `style:` to `hestia.json` **by absolute path** — glow can't expand `~`/`$VARS` there. So it's **path-generalised** (not symlinked): the repo carries `user/glow/glow.yml.j2`, and the `dotfiles` role renders it to `~/.config/glow/glow.yml` with the path templated from `{{ target_home }}` (`docs/repo-structure-design.md` §5; edit the `.j2` + re-run the role to apply).
- `hestia.json` is now a **GENERATED glamour pair** (`hestia-{dark,light}.json`, render.py since M7 PR2; the bootstrap symlinks the `theme_variant` one to the name `glow.yml` points at): **heading hierarchy** — the **H1 title** is the violet `accent` banner (`accent_fg`-on-accent, readable 5.70:1 — white-on-cyan was only 1.94:1), **H2–H6 sections** are cyan `bright_cyan` (dark `#22cdda` / light `#087a84`, both AA). One violet title over cyan sections reads as hierarchy without a full-screen purple wash (the `link` violet stays on inline code + links). **render-markdown.nvim** mirrors this (H1 accent, H2–H6 cyan; `.vimrc`), so vifm's glow view and Neovim's in-buffer markdown agree. And since `glow -p` pipes to **less**, less's status bar (the `:` prompt + `(END)`) is the accent violet too — 256-cube `99` (≈`#7c3aed`, the nearest-cube accent, since violet isn't an ANSI colour), set in `LESS`/`MANPAGER` as `-DP231.99` — matching the H1 banner. Chroma from the `syntax:` table, code blocks on the variant's `surface`.
- **notty caveat:** glow renders **without colour when piped** (e.g. vifm's preview pane) — and worse, leaks malformed empty-param SGR that vifm shows as literal `1m`. To force colour through a pipe set **`CLICOLOR_FORCE=1`** (well-formed, 16-colour SGR); `-s <style>` only carries the style, it does **not** restore colour. A real TTY (the floatterm, full-screen vifm open) renders truecolor and uses the `glow.yml` default automatically.

### imv (`user/imv/config`)
Minimal image viewer config — shrink-to-fit scaling, vim-style `hjkl`/`np` navigation, `HJKL` to pan when zoomed.

**vifm↔imv integrated image + video browsing** (`user/vifm/scripts/imv-browse.sh`, `user/imv/config-vifm`, `user/imv/imv-vifm-return.sh`). In vifm, **opening an image OR video** (Enter/`l`, or vifm's built-in `i` = "handle file" — the image *and* video `filextype` handlers both point here) runs `imv-browse.sh`: it collapses vifm to one pane (`vifm --remote -c only`), `swaymsg split horizontal`, and opens **imv tiled to the right** on the folder's media, started at the cursor file — giving fast full-screen browsing next to vifm (since in-pane graphics never worked here: vifm's preview pane can't render the kitty graphics protocol on this sway/kitty, and previewing per cursor-move lags — so media stays text-info in the pane and *this* is the "see it" path). imv uses a **dedicated config** (`config-vifm`, separate so standalone imv is untouched) that wires it back to vifm over imv's IPC + vifm's client-server (every `--remote` call targets **the launching instance** via `--server-name "$VIFM_SERVER_NAME"` — vifmrc exports it from `v:servername`, and imv inherits it through imv-browse.sh; a bare `--remote` reaches whichever vifm registered the first server name, so with several vifms open the collapse/restore/sync landed in the wrong window — seen live as "the preview pane no longer hides"):
- **Live cursor sync — TWO-WAY (vifm→imv since 2026-07):** imv→vifm is event-driven — each `j/k` is `next/prev 1;exec …/imv-vifm-return.sh`, which `vifm --remote -c "goto '<original>'"`s, so vifm's cursor tracks imv. **`:goto` selects without opening** (a plain `vifm --remote <file>` *opens* the file → would relaunch imv in a loop, and was observed to wedge the server). Two imv gotchas baked in: the `;` has **no leading space** (imv's INI parser strips ` ;…` as an inline comment, silently dropping the chained command), and the logic is in a **script** not inline (imv mangles inline shell quoting in a bind). The reverse — browse in **vifm** and imv follows, so vifm's `/search`+`n`, marks, `gs` etc. stay usable as a media-preview driver — can't be event-driven (vifm's only autocmd is DirEnter), so a detached **watcher** (`imv-browse.sh __watch <dir>`, PID-locked, spawned at launch, exits with imv) polls the launching vifm's cursor via `--remote-expr 'expand("%c:p")'` (~5ms a call, 0.15s cadence) and `imv-msg goto`s imv to it. **Gotcha: `expand()` returns macro values SHELL-ESCAPED** (`my\ pictures`) while handler args / the session map hold raw paths — the watcher sed-unescapes (`s/\\\(.\)/\1/g`) before comparing; unfixed, every comparison failed in any folder with a space, and the dir check closed imv the instant it opened there. Anti-feedback-fight: the return script stamps each imv-originated goto in a **marker file** the watcher consumes-and-skips, and the watcher only acts on a cursor stable for **two consecutive polls** — a fast imv-side `j` run never presents a stable unmarked position, so the watcher can't drag imv backwards. The watcher is also the session's **chaperone**: vifm **leaving the folder** (`expand("%d")` ≠ the session dir) restores the dual-pane preview and **closes imv**; a cursor parked on **anything that isn't this session's media** (unsupported file, a directory, `..`) steers imv onto a trailing **blank "no preview" tile** (plain-ground `blank.jpg`, appended as one extra last imv item so map indexes stay 1:1) — visibly empty rather than frozen on the last image, and no relaunch cost; the return script never syncs vifm onto the blank tile.
- **`q`/`Escape`:** `…/imv-vifm-return.sh quit` — restore vifm's dual-pane preview (`vsplit`+`view!`), sync the cursor, then close imv (`imv-msg $imv_pid quit`, with a `kill` fallback — imv's `exec` swallows the rest of the bind line, so a trailing `;quit` never reaches imv).
- **`h` (up/back, vim-style):** `…/imv-vifm-return.sh up` — close imv and take vifm **up one directory**, cursor on the folder you were browsing. Uses `:goto <dirname-of-image>` (absolute), **not** `cd ..`: the user can change vifm's cwd while imv is open, so the parent is computed from the image's path, not vifm's current dir. (j/k/l/n/N/p still cycle images; prev is on `k`.)
- **Idempotent / re-press, and OTHER imv instances are sacred:** opening another item while **this session's** imv is up doesn't stack a second pane — it `imv-msg $pid goto <index>`s it and focuses **by PID** (`[pid=N]`, not `[app_id="imv"]`); if the item **isn't in the open session** (vifm moved to another directory, or the file is new), the old imv is retired and a fresh session launches on the current dir. The session's imv is identified by a **pidfile, never pgrep**: the launcher `exec`s imv so its own `$$` *becomes* imv's PID (recorded per server name, `/proc/<pid>/comm`-validated against PID reuse) — a bare `pgrep imv-wayland` matches ANY imv, and the teardown used to close a standalone imv / another vifm window's session (caught live). ALL session state is **namespaced by `$VIFM_SERVER_NAME`** (map, locks, marker, pidfile; the thumb cache + backfill worker stay global), so browse sessions in different vifm windows coexist. (This is the whole reason the handler is `imv-browse.sh` rather than a bare `imv` — a plain open spawned a confusing second pane.) imv 4.5 can't sort, so imv-browse.sh launches imv on an explicit list in **vifm's exact view order**: the python pass replicates vifm 0.14's `+name`+`sortnumbers` comparator byte-for-byte (sort.c/utf8.c — NFKD compat-decomposition of the name, skip-leading-zeros, then **glibc `strverscmp` called via ctypes**, the same libc function vifm links, not a reimplementation), verified identical against a live vifm on an adversarial name set. (`sort -V` was the first cut, but coreutils filevercmp ≠ strverscmp — its extension rule, no unicode normalization — and every divergence made the synced cursor **jump**; vifm's order isn't queryable over `--remote` — `expand("%a")` is empty — so we reproduce it.)
- **Videos are faked as images.** imv can't play video, so imv-browse.sh feeds it a **cached ▶ poster thumbnail** for each video (`ffmpegthumbnailer -s 1280` → `magick` composites a play button scaled to the frame; ffmpeg fallback; cached by realpath+mtime). **Priority order (2026-07, after a 2000-video dir wedged the flow):** only the CURSOR file's poster is generated synchronously; other uncached videos show a generic ▶ placeholder and imv launches immediately; a single `nice`/`ionice` background worker (`__backfill` self-invocation, PID-locked) fills the cache sequentially for the next visit. The display list is mapped in **one python pass** (`build_lists`), not a per-file shell loop — the loop's ~6 forks per file were an *independent* ~7s hang at 2000 files even with zero thumbnail work — and that same pass pre-filters the backfill queue to just the missing posters, so a fully-cached dir spawns no worker at all. A PID-checked **launch lock** makes an Enter-storm harmless (the pgrep-imv check can't see the pre-imv window — repeated Enters used to stack launchers). imv only ever sees images. A **session map** (`$XDG_RUNTIME_DIR/imv-vifm-session.<servername>.list`, one `display<US>original` pair per line) resolves imv's current item back to the real file **by display path (`$imv_current_file`), NOT by index**: imv silently *drops* entries it can't load (one corrupt image / unsupported format), shifting every later index — index-resolution made each poster after the bad file "belong" to the wrong video (caught live 2026-07). For the path to be a unique key, each uncached video gets its **own placeholder *hardlink*** (`<thumbkey>.pend.jpg`, pruned at next launch; symlinks don't work — imv canonicalizes them back to `placeholder.jpg`). The cursor sync `:goto`s the **video** (not its thumbnail), and…
- **Enter on a video → mpv** (`…/imv-vifm-return.sh play`): opens mpv **under the vifm+imv combo** (`swaymsg focus parent, split vertical` wraps `[vifm|imv]` and tiles mpv below). **Single-instance, or it fork-bombs:** as focus returns to imv when mpv closes, a spurious Enter (sometimes a train) re-fires the bind. A **PID lock** (`imv-vifm-mpv.lock`) gates it — while a launch/mpv is alive, re-fires just focus the existing mpv; a **debounced cooldown** (the detached wrapper holds the lock until ~2s idle after mpv exits, each re-fire pushing the deadline out) absorbs that train so nothing relaunches; and the lock is **PID-checked** (`kill -0`) so a force-killed mpv leaves no stale lock that dead-ends Enter. (Enter on an image is a no-op — you're already viewing it full-screen. Cost: a ~2s beat after closing mpv before the next video opens.)

True single-window grouping (like the cmus+cava kitty session) isn't possible — imv is a separate Wayland app, not a kitty pane — so the idempotent guard is what keeps the layout from duplicating. Deps: `imv`/`imv-msg`, `swaymsg` (sway), `mpv`, `vifm` server (on by default; `vifm --remote` no-ops if absent), and `ffmpegthumbnailer` + `imagemagick` for the video thumbnails (both in the `terminal` apt group).

### Zathura (`user/zathura/zathurarc` + `theme-{dark,light}`)
Document viewer (PDF/EPUB/DjVu/CBZ — vifm's PDF/comic opener). `zathurarc` keeps behaviour/future settings (direct-edit); ALL colours live in the **GENERATED** `theme-{dark,light}` fragment pair (render.py; `include theme` — the bootstrap symlinks the `theme_variant` one; zathura takes `"#RRGGBB"` and `rgba(...)`). The **UI chrome** is mapped to the palette: statusbar/inputbar/completion/notifications on `bg`/`surface`/`text`, completion + index active rows on `accent`/`accent_fg`, error notification `danger_dark`, warning `yellow`; search highlights are translucent (all matches `blue`, the active match `accent` — the active-match rgba carried the dropped Debian red `rgba(206,0,86,…)` until M7 PR2 fixed it). **Document recolouring follows the variant** — ON on dark (`recolor true`: white pages flip to the ground, black text to `text`; `recolor-keephue true` keeps coloured text readable), OFF on light (pages are already light); both variants carry sensible recolor values, so **`r`** still toggles per-document either way. Like swaylock, annotations are kept on their **own lines** (no trailing inline comments).

### Git (`user/git/`)
Default branch `main`, editor `vim`, commits GPG-signed. Global excludes at `~/.gitignore_global` (`user/git/.gitignore_global`, symlinked): the Claude `settings.local.json` and common macOS/Node/Vim/VS Code artefacts. It deliberately does **not** exclude `.gitignore`/`.editorconfig` — those are meant to be committed and shared per-repo, and a global exclude only applies on this machine so it wouldn't travel to clones/collaborators/CI anyway. Rule of thumb: only *never-commit-anywhere* noise goes in the global file; project ignores belong in a committed `.gitignore` (e.g. this repo's, protecting `bootstrap/host_vars/*.yml`); "just this clone" ignores go in `.git/info/exclude`. `core.excludesfile` uses git-native `~` expansion (`~/.gitignore_global`), and the gitconfig is **rendered** (`user/git/.gitconfig.j2`, not symlinked) so `gpg.program` templates from `{{ repo_root }}` — neither needs a manual edit on a home/repo move (`docs/repo-structure-design.md` §5). When `enable_claude_user` is on, the rendered gitconfig also adds a **`[safe] directory = {{ claude_shared_tree }}/*`** block (trailing-wildcard, git 2.36+): the shared `/srv/devshare` tree is owned by the `claude` agent user, so without it git trips "dubious ownership" (CVE-2022-24765) when **dimitrios** operates on those repos. The block is Jinja-gated on the toggle — no agent user → no claude-owned tree → no entry rendered. No HTTPS credential helper is configured — auth is over SSH (`git@github.com`), so an HTTPS remote would simply prompt; add `helper = cache` for an in-memory, no-plaintext fallback if ever needed (avoid `helper = store`, which writes plaintext to `~/.git-credentials`). ### Sway (`user/sway/config`)
Wayland compositor config. Notable points:
- **Keyboard** (`input type:keyboard`): `xkb_layout "us,de,gr,bg"` + `xkb_variant ",,,phonetic"` — Bulgarian uses the **traditional phonetic** variant (W → в); commas align variants to layouts. `xkb_options grp:alt_shift_toggle` — **Alt+Shift** cycles layouts; Caps Lock is stock (no remap — the earlier `caps:super` mapping was reverted).

This is the supported way to show Claude Code an image: claude runs as a **separate user, walled off from this session's Wayland clipboard socket** (`/run/user/<dimitrios>`, `0700`), so a `Ctrl+V` image paste into Claude Code **can't work** — and opening that socket would expose every copied image/password. Sharing stays **explicit** (only `$mod+Print` shots are claude-visible) — take one, then tell claude "look at the screenshot". `shared` **falls back to the local dir** when `/srv/clipshare` is absent (a spin without `claude_user`), so the binding always works; the `notify-send` shows where the file landed. (The script also `mkdir -p`s the dir — fixing a latent bug where the old inline `Print` binding wrote into a possibly-missing `~/Pictures/Screenshots`.) Symlinked into `~/.config/sway/scripts/` like `start-waybar.sh`.
- **Screen-sharing env export:** `exec dbus-update-activation-environment --systemd WAYLAND_DISPLAY XDG_CURRENT_DESKTOP XDG_SESSION_TYPE` pushes the session env into the D-Bus/systemd user activation environment so `xdg-desktop-portal` activates with the right context. Required for screen sharing — see the **Screen sharing** section. `exec` (not `exec_always`) runs once at login; it does **not** re-run on `swaymsg reload`, so apply live after editing with the same command.
- **PolicyKit auth agent:** `exec sh -c '[ -x /usr/libexec/polkit-mate-authentication-agent-1 ] && exec …'` starts **mate-polkit** at login. A sway session runs no polkit agent by default, so any GUI privilege prompt — nemo's "Open as Root" (gvfs `admin://`, `gvfsd-admin` is present), mounting a system disk, a `pkexec` call — is **silently denied** because polkit has no agent to raise the password dialog. mate-polkit is the **GTK3** agent (`mate-polkit` in the `wayland` apt group), so the dialog themes with hestia/adw-gtk3. Guarded on the binary (a spin without it skips cleanly); `exec` once at login, placed **after** the `dbus-update-activation-environment` line so it registers on the right session bus.
- **Default file manager (nemo) — `user/sway/nemo-setup.sh`:** `exec …/scripts/nemo-setup.sh` at login runs the session-time nemo wiring. Three things: (1) **"Open in Terminal"** — nemo reads `org.cinnamon.desktop.default-applications.terminal`, whose schema default `gnome-terminal` isn't installed, so the item silently no-ops; the script points it at **alacritty**, the default terminal (`exec-arg -e`). (2) **default folder handler** — `xdg-mime default nemo.desktop inode/directory` (folders opened from any app land in nemo). (3) **disables the `90_new-launcher.nemo_action`** launcher action, which Depends on `cinnamon-desktop-editor` (a Cinnamon package hestia doesn't ship) and otherwise logs `missing dependency: cinnamon-desktop-editor` at startup + shows a dead menu entry — turned off via `org.nemo.plugins disabled-actions`, no cinnamon install. The whole script self-guards on `command -v nemo` (a spin with `enable_file_managers=false` has no nemo, hence no `org.cinnamon.*`/`org.nemo.*` schemas → clean no-op, not a "No such schema" error). It's a **script, not an inline `exec sh -c`**, because the action's GVariant value (`['90_new-launcher.nemo_action']` — single quotes inside an array) doesn't survive sway's config-line quoting layered on its own `sh -c`. `exec` once at login (dconf + `mimeapps.list` persist); a relogin re-asserts.
- **Session-script `exec` paths are path-generalised:** `exec …/credential-unlock.sh` and `exec_always …/start-waybar.sh` reference **`$HOME/.config/sway/scripts/…`** (sway runs `exec` via `sh -c`, so `$HOME` expands) — no clone-absolute path. `start-waybar.sh` is **symlinked** there; **`credential-unlock.sh` + its sibling `keyring-ssh-askpass.sh` are *rendered* there** (they carry identity values — `ssh_key_file` / `gpg_keygrip` / `git_signingkey` from host_vars), both into the same dir so `credential-unlock.sh` finds the sibling via `readlink -f "$0"`.
- **Launcher / GPU render-path selection (`system/sway-session/start-sway`):** sway isn't started by the config above — greetd runs **`/usr/local/bin/start-sway`** (`tuigreet … --cmd start-sway`), which sets the Wayland session env then `exec sway`. On a host with an NVIDIA GPU **and** another GPU (AMD/Intel) present, sway renders on the other GPU while NVIDIA stays available purely as a scanout target for any monitors wired to it (wlroots' built-in multi-GPU "reverse PRIME": the secondary GPU gets its own local renderer solely to import/texture the primary GPU's rendered buffers for its own scanout). Both GPUs are detected via `/sys/class/drm/card[0-9]/device/vendor` (vendor `0x10de` = NVIDIA) and listed in `WLR_DRM_DEVICES`, non-NVIDIA first; `WLR_RENDER_DRM_DEVICE` pins the actual renderer to the non-NVIDIA GPU's **render node** specifically (its `renderDN` path, resolved from `/sys/class/drm/renderD*/device`, matched against the card's own PCI device — not its `cardN` node, which wlroots rejects as a render target). Root-caused + live-tested 2026-08-22 on hephaestus (AMD Raphael iGPU + NVIDIA RTX 4060): with NVIDIA as the wlroots render GPU, Chrome/Chromium windows would intermittently go fully blank or render text at the wrong position — a different, worse bug than the hover/repaint flicker already fixed by forcing XWayland (below); rendering via Mesa/radeonsi instead fixes it, confirmed on that GPU's own outputs. **Known residual issue**: a monitor scanned out via NVIDIA (reverse PRIME) still flickers even with the other GPU rendering — likely the same implicit-sync weakness in this driver (550.163, predates `EGL_ANDROID_native_fence_sync`) affecting NVIDIA's own scanout/present path regardless of which GPU rendered the buffer; `WLR_RENDERER=vulkan` does **not** help here (confirmed) — Vulkan's device selection ignores `WLR_RENDER_DRM_DEVICE` entirely and grabs the discrete GPU outright, reintroducing the original bug. Accepted as unfixed for now, same category as the residual XWayland flicker below. NVIDIA stays fully available for CUDA/NVENC/PRIME render-offload (Steam, ffmpeg) too — unaffected, since those go through `/dev/nvidia*` directly, not this render path. `--unsupported-gpu` stays mandatory even though NVIDIA isn't the renderer: sway's proprietary-driver guard fires on any *opened* nvidia-drm device regardless of which GPU actually renders. Without `WLR_RENDER_DRM_DEVICE`, wlroots picks a GPU's `boot_vga`/BIOS-primary flag as a renderer tiebreak, independent of `WLR_DRM_DEVICES` listing order — confirmed live; NVIDIA was `boot_vga` on this host, so listing order alone wasn't enough. The NVIDIA-specific env (`GBM_BACKEND=nvidia-drm`, `__GLX_VENDOR_LIBRARY_NAME=nvidia`, `WLR_NO_HARDWARE_CURSORS=1`, `NVIDIA_DRIVER_CAPABILITIES=all`, `WLR_RENDERER=vulkan`) + `--unsupported-gpu` are applied **only when NVIDIA is the sole live GPU** (guarded on `/dev/nvidia0` / the `nvidia` entry in `/proc/modules`) — on AMD/Intel-only hosts they'd break rendering, so they're skipped. Both `start-sway` and the **greetd `config.toml`** that calls it are tracked (`system/sway-session/`) + deployed by the **`sway_session`** role (greetd config → `/etc/greetd/`, applied on next login — the role doesn't restart greetd). Only installing greetd/tuigreet themselves is a prereq (`system/sway-session/README.md`).

- **Idle inhibition (the "caffeine" replacement):** the auto-lock chain is `swayidle` (**pre-lock dim warning at 270s** → lock at 300s → DPMS-off at 600s) → `swaylock` (now reads `~/.config/swaylock/config`, hestia-themed — see the **Swaylock** section; the invocations carry no `-c`, so the config's `color` is the lock background). The **270s warning** dims *every* output to 40% via a **backgrounded `gammastep -O 6500 -b 0.4 &`** software-gamma drop (killed by `pkill -x gammastep` on the timeout's `resume`) **and** raises a persistent `notify-send -u critical -t 30000` notice (matches mako's `[urgency=high]` red style, stays the full 30s — previously it used the 5s default-timeout, so the warning vanished 25s before the lock). **gammastep must be backgrounded:** on Wayland its `-O` "one-shot" doesn't actually exit (wlroots resets the gamma ramp the instant the setting client disconnects, so gammastep stays alive to *hold* the dim) — and `swayidle -w` waits for each timeout command to finish, so a foreground gammastep would wedge swayidle forever (no resume fired, no lock). Backgrounding lets `notify-send` return; `resume` then `pkill`s gammastep (the disconnect restores brightness) **and dismisses the warning notice** — the `-t 30000` would otherwise leave it on screen for the full 30s after input already cancelled the lock, so `notify-send -p` stashes the notification id in `$XDG_RUNTIME_DIR/lock-warn.id` and `resume` runs `makoctl dismiss -n <id>` to clear that one (not `-a`, which would drop unrelated notifications on every wake). The dim is the real cue: this is a **desktop with external DisplayPort monitors and no `/sys/class/backlight`**, so `brightnessctl` can't dim the panels (the `XF86MonBrightness` keybinds are no-ops on this hardware) — software gamma dimming hits both 32" screens at once regardless of which has focus. Any input before 300s fires the resume (full brightness back, no lock). gammastep is in the apt manifest's `wayland` group. To stop it locking during fullscreen video, sway's native `inhibit_idle fullscreen` is set per media app — `for_window [app_id="firefox"|"chromium"|"mpv"|"^FFPWA-"] inhibit_idle fullscreen` — so those windows raise a Wayland idle inhibitor *while fullscreen* (swayidle honours it; the timers pause, then resume on un-fullscreen). Deliberately **scoped to media apps**, not `[app_id=".*"]`: a blanket rule would let a forgotten fullscreen terminal skip the auto-lock (the security boundary). `app_id` is unanchored regex, so `firefox` also matches `firefox-esr`, and **`^FFPWA-` matches every `firefoxpwa` web app** (Netflix, YouTube, …) — each PWA gets its own `FFPWA-<ULID>` app_id (not `firefox`), so the prefix match is what actually catches the common "fullscreen Netflix in a PWA" case; add a browser = one more line. (mpv also self-inhibits via `--stop-screensaver` by default; the sway rule is the belt-and-suspenders that doesn't depend on the app speaking the `idle-inhibit` protocol.)

Apply most config changes with `swaymsg reload`.

### Screen sharing / xdg-desktop-portal (`user/xdg-desktop-portal/sway-portals.conf`)
Wayland screen sharing (Teams/Edge, OBS, etc.) goes through **PipeWire** + **xdg-desktop-portal**. On Sway the screencast backend is **`xdg-desktop-portal-wlr`** (wlroots); other portal interfaces (file picker, settings) fall to **`xdg-desktop-portal-gtk`**.

- **`sway-portals.conf`** routes interfaces per backend (matched to this session via `XDG_CURRENT_DESKTOP=sway`): `ScreenCast`/`Screenshot` → `wlr`, everything else `default=gtk`. Without explicit routing the portal can misroute screencast to gtk (which can't capture on wlroots) and silently fail. If gtk is ever uninstalled, the `default` must change (wlr only implements ScreenCast/Screenshot — no file picker). **`Settings` is also pinned to `gtk` explicitly** (`org.freedesktop.impl.portal.Settings=gtk`): once the Qt-theming track pulled in **`xdg-desktop-portal-kde`** (via `plasma-integration`, for dolphin/krusader), *two* backends declare the Settings impl and `default=gtk` alone doesn't stop the kde one from answering the **`color-scheme`** query — it reported "no preference", so libadwaita/GTK4 apps that read the portal (**file-roller's Compress dialog**, nautilus) fell back to **light** while GTK3 apps stayed dark via `GTK_THEME`. The explicit pin makes gtk answer from gsettings `color-scheme` (see the dark-mode bullet below). Diagnose with `gdbus call --session --dest org.freedesktop.portal.Desktop --object-path /org/freedesktop/portal/desktop --method org.freedesktop.portal.Settings.ReadOne org.freedesktop.appearance color-scheme` → `2` = dark.
- **Session env:** the portal must inherit `WAYLAND_DISPLAY`/`XDG_CURRENT_DESKTOP` via the Sway `dbus-update-activation-environment` exec line (see Sway section). The portal is **D-Bus-activated on demand** (first screencast request), so the env must be exported *before* it first activates — a fresh login handles this.
- **Monitor-only capture:** the wlr backend reports `AvailableSourceTypes=1` (MONITOR only) — **per-window sharing is not supported** on Sway; share a whole output. Workaround: isolate the app on the second monitor and share that output. May change once the `wlr` portal adopts `ext-image-copy-capture` toplevel sources.
- **Dark mode (color-scheme):** the gtk backend exposes `org.freedesktop.appearance color-scheme` via the **Settings** portal, which Firefox and other portal-aware apps read. Force dark with `gsettings set org.gnome.desktop.interface color-scheme prefer-dark` (needs `dconf-cli` + `libglib2.0-bin`); without it the portal reports `0` (no preference) and apps default to **light**. This surfaced right after the portal was first installed — Firefox flipped to a light theme until the setting was applied. **Now set at login** by the sway theme fragment's `exec` (per `theme_variant` — `prefer-light` on the light desktop), so it's reproducible — see the **GTK / Adwaita** section.

**External dependencies** (install on a fresh system):
- `pipewire`, `pipewire-pulse`, `wireplumber` (usually present; the audio stack).
- `xdg-desktop-portal` + `xdg-desktop-portal-wlr` (screencast) + `xdg-desktop-portal-gtk` (file picker/other portals).
- `dbus-bin` provides `dbus-update-activation-environment` (used by the Sway env-export exec line).

### Waybar (`user/waybar/config`, `user/waybar/style.css`, `user/waybar/scripts/`)
Top bar; files symlinked into `~/.config/waybar/`. Reload with `killall -SIGUSR2 waybar` (or `killall waybar; waybar &`). Colours are `@define-color` tokens in the **GENERATED** `theme-{dark,light}.css` pair (render.py), `@import`ed by `style.css` as `theme.css` (the bootstrap symlinks the `theme_variant` one) — edit `palette.yml` + re-render, not the fragment; `style.css` itself references only `@token` names.

**Single launcher + boot race:** waybar is started by sway's `exec_always` line running `start-waybar.sh` and must be the *sole* launcher. Two boot problems, two fixes: (1) a globally-enabled `waybar.service` user unit double-started it — disabled with `sudo systemctl --global disable waybar.service`; (2) even solo, waybar launched before the compositor could map its layer-shell surface, so the bar didn't render until a `$mod+Shift+c` reload. `user/sway/start-waybar.sh` fixes (2) — it kills any instance, settles, and waits for an active output before `exec waybar`. (The session is greetd-launched, not systemd-managed, so a `graphical-session.target`-ordered user service isn't an option without extra plumbing.)

- **Font:** the **bar** uses `BigBlueTermPlus Nerd Font Mono` at 16px (`style.css`, the `*` rule). Bitmap-derived — keep its sizes at integer pixel-grid values (16/24/32) for crispness. **Not** the `437` variant: that one is the literal DOS code-page-437 build, which has no Greek *alphabet* (only ~12 Greek/math *symbol* glyphs — α π Σ Ω δ ε σ τ …), so a non-Latin window title (`sway/window`) rendered its `ε` as a euro-like lunate epsilon and fell back mid-word for every letter CP437 lacks. `Plus` is the same bitmap typeface with full Greek (and Cyrillic etc.) plus the same Nerd Font icon glyphs, so the look is unchanged but titles render cleanly. **Tooltips** are restyled via `tooltip`/`tooltip label` rules: `Lilex Nerd Font Mono` 17px (scalable, cleaner than the bitmap bar font, also full Greek coverage), on the unified `#1a1a1a` bg with a 1px violet-accent border + padding (GTK tooltips are otherwise translucent/borderless).
- **Icon alignment:** module icons are wrapped in inline Pango markup `<span size='xx-large' rise='-3072'>…</span>`. The `rise` is a hand-tuned vertical offset (Pango units, 1/1024 pt); re-tune if the font changes.
- **PUA glyph caveat:** editing tools can silently strip Private-Use-Area (Nerd Font) glyphs, leaving an empty `<span></span>`. If an icon renders as blank space, insert the codepoint via a small Python write and verify, rather than re-typing it.
- **Modules**: left side leads with **`custom/launcher`** (see below), then the sway workspaces/mode; right side: `custom/cpu`, `memory`, `custom/gpu` (all GPUs, see below), `power-profiles-daemon`, `custom/audio`, `custom/language`, `custom/network`, `bluetooth`, `custom/usb`, `custom/notifications`, `custom/weather`, `custom/clock`, `custom/power` (see below). Right-side modules share styling via a grouped CSS selector — add new ones to that group.
- **Width-tier responsiveness** (`user/waybar/scripts/lib-density.sh`, 2026-08): a shared `hestia_density()` shell function, sourced by `clock.sh`/`network.sh`/`language.sh`/`weather.sh`/`audio.sh`, that shrinks their bar TEXT on a narrow output — the demo screenshot that prompted this (a `hestia-shot` capture at 1280×720) came out with most of the bar occupied by widgets, several of them cut off. Queried **live, per poll**, against the currently-**focused** sway output's pixel width via `swaymsg -t get_outputs` (parsed with a small `awk` pass — the output's own `rect` block always precedes its own `focused` key in swaymsg's JSON, so no `jq`/python dependency was needed) — deliberately **not** a static host_var: the same machine can have a small laptop panel and a large external monitor plugged in at once, and a per-host setting would be wrong for whichever one it didn't match. Three tiers, `full`/`compact`/`minimal` at ≥1600px/≥1100px/below (tuned against `docs/video-capture-design.md`'s measured resolutions and common real displays, freely adjustable — nothing else depends on the exact numbers): `clock.sh` drops the date at `compact`, seconds too at `minimal`; `network.sh`/`weather.sh`/`audio.sh` go icon-only at `minimal` (their `compact` is identical to `full` — a single icon+value pair has nothing left to trim before the icon-only floor); `language.sh` likewise. Untouched: `custom/cpu`/`memory`/`custom/gpu`/`custom/usb` and the other single-glyph modules — not asked for, and `cpu`/`gpu`/`memory`'s bar text is already just a 2-3 char number, nothing meaningful left to drop.
- **Fixed-width numeric values** keep the bar from resizing as values change width (e.g. `0%`→`100%`): percentages are right-padded to **2 digits** — script modules via `printf '%2d%%'` (`cpu.sh`/`gpu.sh`/`network.sh`), the one remaining built-in via a fmt spec in its format string (`memory`'s `{used:>4.1f}`). (2 not 3: it reserves up to `99%`; the rare `100%` adds one char — an acceptable jump.) Leading spaces render fine in the bar label.
- **Click handlers** open floating TUIs as toggles so a second click closes the popup. Two toggle styles: for a known process name, `pgrep -u $USER -x NAME && pkill -u $USER -x NAME || alacritty --class floatterm -e NAME` (network/bluetooth/audio) — **always `-u $USER`-scoped**: bare pgrep matches other users' processes too, and the `claude` agent runs these same apps headlessly on this box (caught live 2026-07: a leftover claude `imv-wayland` made vifm's image-open silently no-op). For the script-launched ones whose final process name isn't predictable (gpu/weather), **do NOT use `pgrep -f SCRIPT`** — it self-matches the launcher's own `sh -c` cmdline (which contains SCRIPT), so the first click kills the launcher and nothing opens. Toggle via the **sway window tree** instead: `swaymsg -t get_tree | grep -q floatterm-NAME && swaymsg '[app_id="^floatterm-NAME$"] kill' || alacritty --class floatterm-NAME -e …` (the tree query sees actual windows, not process cmdlines; the unique `floatterm-NAME` app_id still floats under the existing `[app_id="floatterm"]` rule — sway app_id criteria are unanchored regex). These were kitty windows launched with `-o confirm_os_window_close=0` until the terminal-emulator evaluation (docs/roadmap.md) swapped the default to Alacritty — kitty pops its own "still running, close anyway?" dialog when the WM kills a window mid-program, Alacritty has no such prompt at all, so the sway-tree toggles needed no replacement flag, one whole workaround simply stopped being necessary.
  - `custom/cpu` / `memory` → both toggle the same `htop` (`pgrep -x htop`; `htop` is in the apt manifest).

### Alacritty (`user/alacritty/`) — the default terminal
Terminal-emulator evaluation **verdict** (2026-08, `docs/roadmap.md`'s "Terminal emulator" row, `showcase/terminal-emulator.md`): **Alacritty is the DEFAULT**, replacing kitty everywhere sway/waybar spawn a terminal (`$mod+Return`, every floatterm popup, nemo's "Open in Terminal", the USB-mount vifm launcher — `set $term alacritty` in `user/sway/config`). Font `Lilex Nerd Font Mono` at 11pt (matched to kitty's, so the trial compared the terminals, not the font), padding/scrollback matched to kitty too (`user/alacritty/alacritty.toml`). `decorations = "None"` (tiling WM, no title bar). Colours are a **GENERATED** `theme-{dark,light}.toml` pair (`render_alacritty()` in `themes/hestia/render.py`, from `palette.yml` — promoted from hand-authored 0.11.0, same pass that promoted tmux/zellij, `[general] import` pulls in the `theme_variant` one as `theme.toml`). One genuinely nice discovery: Alacritty's **own bundled terminfo entry already advertises SGR mouse** (`infocmp -x alacritty` shows `XM=`/`kmous=\E[<`) — unlike kitty (see below), vifm's scroll wheel just works under Alacritty with **no terminfo override needed at all**.

- **Vi mode is vim-themed where vim has something worth matching, accent-branded where "vim-themed" would mean off-brand.** **Selection** (`[colors.selection]`) is the accent fill — `#7c3aed`/`accent_fg` white text, both variants — matching kitty's `selection_background`, vifm's `Selected`, and Windows Terminal's `selectionBackground`. It briefly matched vim's `Visual` group *literally* instead (0.11.0: dark `#5fd7ff` cyan fill/black text, light `#0087d7` blue fill/white text, `gui=reverse` unpacked from the vim source, promoted to `palette.yml`'s `extended.visual` once Alacritty became a second consumer of a value that used to be a `render_vim()`-only literal). That cyan was inherited unchanged from upstream wildcharm's own `Visual` group — never re-anchored on the Memphis brand (0.9.0 only touched `syntax:`), so it read as "close to hestia cyan but not quite" next to the real ANSI/brand teal, which is exactly what gave it away on a low-quality monitor. 0.12.0 dropped `extended.visual` entirely and re-pointed both `render_vim()`'s `hi Visual` and `render_alacritty()`'s `[colors.selection]` at `roles.accent`/`accent_fg` directly, so selection is now branded the same way everywhere. **Search** doesn't reuse zathura's "all-matches-blue/active-accent" language — Alacritty's `search.matches`/`search.focused_match` split isn't active-vs-inactive, it's "every match" vs. "the one the cursor is on," which is *exactly* vim's `Search`/`CurSearch` split (`hestia.vim` links `CurSearch` → `IncSearch`): `focused_match` gets `IncSearch`'s orange (`syntax.type`), `matches` gets `Search`'s green (`syntax.string`), live-verified by driving real vi-mode search with `wtype` and screenshotting both the live-typing state (orange nearest-match + green others) and the post-Enter state (Alacritty drops the "focused" distinction once the search UI closes — its own behaviour, not a theming gap). **Line indicator** (`[colors.line_indicator]`, the scrollback-position HUD, top-right during search/vi-mode) is `bright_cyan`, left at Alacritty's `None`/`None` default until this pass.

Second try: keep `Block` but shade vi mode's cursor `accent_dark` instead of `accent` — read as "a darker purple, why?" rather than a clear signal, also reverted. Landed on: **same accent `#7c3aed`, same `Block` shape, in both modes** (`[cursor]` in `alacritty.toml`) — the mode is obvious enough from context (what you just pressed, the line indicator, search behaviour) that the cursor itself doesn't need to change. The lesson generalises: a "make X visibly different" instinct isn't automatically right — verify live before committing to it.

### Kitty (`user/kitty/kitty.conf`, `user/kitty/music.session`) — companion, not dropped
Kept installed and themed after losing the terminal-emulator evaluation (above) for two concrete, still-live reasons: **ranger**'s `preview_images_method kitty` needs a real kitty window for its in-pane image previews (kitty's graphics protocol; ranger is a themed file-manager-evaluation runner-up, not the default — vifm doesn't need this), and `$mod+m`'s music session used kitty's own `--session`/layout feature until it was rebuilt on tmux (see Alacritty, above; `music.session` itself is left in place, still usable manually via `kitty --session music.session`). Font `Lilex Nerd Font Mono` at 11pt; `ctrl+shift+=/-/0` adjust size. **Color emoji** (e.g. `✅` in program output) need **`fonts-noto-color-emoji`** (apt) — Nerd Fonts don't carry the Unicode emoji set, so without it emoji render as tofu (double-width empty boxes). kitty reaches it via fontconfig fallback and is presentation-aware (text glyphs like `✓`/`✗` stay in the primary font), so **no `symbol_map`** is set — a broad one would wrongly force those text symbols into the emoji font. Colours live in the **GENERATED** `theme-{dark,light}.conf` fragment pair (render.py; `include theme.conf` — the bootstrap symlinks the `theme_variant` one): 16-colour palette re-anchored on the Memphis brand (light = upstream's light ANSI table); cursor/selection/active-tab use the violet accent `#7c3aed` in both variants (ANSI red stays the separate color1 red). kitty resolves the include against the literal `~/.config/kitty/` path (not the symlink target), where the theme.conf link lives.

**SGR-mouse terminfo override (`user/kitty/xterm-kitty-sgr-mouse.terminfo`).** kitty's stock `xterm-kitty` terminfo advertises only the **legacy** X11 mouse protocol (`kmous=\E[M`, no `XM`), so ncurses apps negotiate mode-1000 mouse — whose **wheel** events (buttons 4/5) **vifm ignores**. That's why vifm's `set mouse=a` gave working clicks but a **dead scroll wheel** (and grabbing the mouse also disables kitty's own arrow-key scroll fallback, so the wheel went fully dead). kitty itself fully speaks **SGR mouse (mode 1006)** — only its terminfo omits the capability (Alacritty's own bundled terminfo doesn't have this bug — see above, no override needed there). The fix is a tracked terminfo source that layers the SGR caps (`XM`/`xm` + `kmous=\E[<`, lifted from `xterm-256color`) onto kitty's entry via `use=xterm-kitty`, compiled into `~/.terminfo` by the **dotfiles role's `terminfo.yml`** (no root). ncurses then negotiates SGR mouse (`\E[?1006;1000h`), so vifm handles **both click and wheel** — one notch = one line (`<ScrollWheelDown>`=`<c-e>`), no `wheel_scroll_multiplier` tuning needed (scrollback stays fast). Recompiling is idempotent (`use=` resolves to the system entry first, the override after — never circular). **`terminfo_type none` in `kitty.conf` is REQUIRED for the override to take effect** — kitty defaults to `terminfo_type=path`, which exports `TERMINFO=/usr/lib/kitty/terminfo` in every child, and since ncurses searches `$TERMINFO` first that *shadows* `~/.terminfo` (the whole reason the override initially appeared to do nothing — `infocmp -x xterm-kitty` showed no XM until `TERMINFO` stopped pointing at kitty's bundle). `none` makes kitty set no `TERMINFO`, so the normal search (`~/.terminfo` first, then system db) applies and the override wins; it covers every kitty child including `kitty -e vifm` (the USB-mount handler). An `env TERMINFO=…` directive would *not* work — kitty overwrites `TERMINFO` after applying user `env` (`kitty/child.py`). To check: `infocmp -x xterm-kitty | grep XM` (note the **`-x`** — `XM` is an *extended* cap, invisible to plain `infocmp`). Verified via pty injection: SGR wheel scrolls vifm; legacy wheel is a no-op. Apply live with `tic -x -o ~/.terminfo user/kitty/xterm-kitty-sgr-mouse.terminfo`, then fully restart kitty.

### Windows Terminal (WSL) (`themes/hestia/dist/windows-terminal/`, `themes/hestia/deploy-windows-terminal.py`)
Themes the **Windows-side terminal** for the WSL access pattern the tmux/zellij/mosh section below is built around (a work laptop's WSL distro, SSH/mosh into hephaestus) — not a desktop app, so it's outside `docs/roadmap.md`'s catalog and outside `site.yml`: WSL is a separate machine the Ansible bootstrap was never meant to reach, same "deliberately NOT Ansible-managed" category as NVM/vim-plug/GitHub onboarding. `render_windows_terminal()` (`themes/hestia/render.py`) emits **one** GENERATED artifact, `dist/windows-terminal/hestia-schemes.json` — a Windows Terminal **[JSON Fragment Extension](https://learn.microsoft.com/windows/terminal/json-fragment-extensions)** carrying **both** `hestia-dark` and `hestia-light` colour schemes in a single file (a deliberate exception to the usual `theme_variant` dark/light pair: Windows Terminal already has its own scheme picker in Settings, so there's no host-side variant switch to drive here). Field mapping mirrors `render_kitty` (the repo's canonical 16-colour definition): `background`=`bg`, `foreground`=`text`, `cursorColor`/`selectionBackground`=`accent`, all 16 ANSI slots from `palette.yml`'s `ansi:` table (Windows Terminal calls the magenta slot `purple` — same colour, different field name).

**Deploy is a one-time manual step from inside WSL**, `themes/hestia/deploy-windows-terminal.py` (`--variant dark|light`, default dark) — never wired into the bootstrap, and it never edits the user's own `settings.json`: fragment JSON files are auto-merged by Windows Terminal at launch from a well-known folder, so the deploy script only ever *writes new files there*. It copies the rendered schemes fragment into `%LOCALAPPDATA%/Microsoft/Windows Terminal/Fragments/hestia/` — **the one folder Windows Terminal scans for third-party fragments, regardless of install variant** (Store package, unpackaged/winget, Preview, Canary — confirmed live 2026-08-19; an earlier version of the script wrongly branched on which install's `settings.json` existed and wrote into a Store package's own `Packages\...\LocalState\Fragments`, which is a *different*, unrelated mechanism — for a Store app declaring itself as an extension via its own appxmanifest — that Windows Terminal never scans on disk, so nothing loaded; the script now also auto-removes any stale files it finds there from that earlier bug) — then computes the **current WSL distro's own Windows-Terminal-auto-generated profile GUID** and writes a second small fragment patching *that* profile's `colorScheme`/`cursorColor`/`tabColor` (both accent `#7c3aed`) — not a guess: Windows Terminal derives that GUID deterministically from the distro's registered name (UUIDv5 over a fixed namespace GUID, UTF-16LE-encoded per MS's documented recipe), and that registered name **is** `$WSL_DISTRO_NAME` inside the distro, so the script computes the exact same value Windows Terminal did (verified against MS's own worked example: `profile_guid("Ubuntu")` reproduces their documented `{2c4de342-...}` exactly). Idempotent (always overwrites both files); a safe no-op if the GUID ever matches nothing (e.g. an already-renamed profile) — Windows Terminal just ignores an `"updates"` that targets no profile. Windows Terminal only picks up fragments on its next launch/new tab, not live (and the OLD process must actually exit — closing every window doesn't always kill it; check Task Manager for a lingering `WindowsTerminal.exe` if a re-launch doesn't pick up the change). Scope is deliberately terminal-chrome-only for now — the WSL-side dotfiles (bash/vim/tmux/vifm/bat/…) that would make the *shell* match too are a separate, larger "trimmed bootstrap for a foreign machine" problem, not yet started.

Solves working from a remote terminal (the motivating case: a work laptop's WSL Ubuntu, SSH/mosh into hephaestus) where "another terminal" previously meant a whole new SSH login.

- **tmux** (`user/tmux/.tmux.conf`): mouse support, vi-style copy-mode (`setw -g mode-keys vi`) and pane navigation (`h/j/k/l`, additive to the default arrows — matches `set -o vi` bash and vim elsewhere), 1-indexed windows/panes, splits on the mnemonic `|`/`-` (kept alongside tmux's stock `%`/`"`) opening in the current pane's cwd, and a **TPM** bootstrap for `tmux-resurrect`/`tmux-continuum` (session persistence across a reboot) — TPM itself is a one-time manual `git clone ~/.tmux/plugins/tpm`, deliberately **not** Ansible-managed, same shape as vim-plug. **Themed** via a **GENERATED** `theme-{dark,light}.conf` pair (`render_tmux()` in `themes/hestia/render.py`, from `palette.yml` — promoted from hand-authored 0.11.0), symlinked by `theme_variant` to `~/.config/tmux/theme.conf` and pulled in via `source-file -q` from `.tmux.conf`: session-name and active-window get an accent-filled chip (`#7c3aed` bg / white text, mirroring kitty's active-tab treatment), pane borders follow the idle(`border`)/active(`accent`) split used elsewhere (swaylock's ring states), copy-mode selection and the command-prompt/message line are accent-filled too.
- **zellij** (`user/zellij/config.kdl`; not in Debian apt, so it rides the `localbin` role as a pinned, sha256-verified release binary — same shape as yazi — gated `enabled` on the same `enable_multiplexers` toggle): mouse mode, Wayland clipboard (`wl-copy`), and its own built-in session serialization (native equivalent of tmux-resurrect, no plugin needed). **Themed** via a **GENERATED** `hestia-{dark,light}.kdl` theme pair (`render_zellij()`, promoted from hand-authored 0.11.0) — zellij auto-loads any `.kdl` under `CONFIG_DIR/themes/`, so the pair is symlinked by `theme_variant` to `~/.config/zellij/themes/hestia.kdl` and selected variant-blind with `theme "hestia"` in `config.kdl` (same shape as vifm's `colorscheme hestia`). Zellij's theme schema (0.44) is per-UI-role (`text_unselected`, `ribbon_selected`, `frame_selected`, …), each taking RGB **decimal** `base`/`background`/`emphasis_0..3` — far more granular than tmux/kitty's flat ANSI-ish model, so `render_zellij()` uses a small `rgb()` hex→decimal helper and maps each role back to the same handful of hestia roles (accent fill on the active ribbon/frame — the zellij analog of tmux's active-window chip and pane-active-border — `surface`/`surface_alt` for selected rows, the ANSI green/yellow/blue/magenta/bright_cyan spread across the `emphasis_*` slots). Bare `0` fields are zellij's single-index EightBit colour form, kept literal rather than invented into a role.

**mosh** (apt package only, `enable_mosh`, default on, no role — gates the `mosh` apt group) rides an existing SSH login to authenticate (so it inherits whatever sshd hardening is in place, e.g. the opt-in `ssh_server` role's TOTP requirement — confirmed live: `mosh` prompts for the same TOTP code as a plain SSH login before connecting), then hands off to a UDP session with client-side speculative local echo — it displays predicted input immediately and reconciles once the server actually replies, so typing stays responsive and nothing is lost across a **roaming** network change (verified live: toggling wifi off/on mid-session on a work laptop left the tmux session running with zero reconnect, vs. a plain SSH+tmux session which would have gone silent and needed a full reconnect + reattach). Mosh has no scrollback/multiplexing of its own — it's meant to run *underneath* tmux, not replace it. Needs a **UDP port range forwarded on the router** to the target host's LAN IP (mosh-server picks a free port per session from that range, e.g. `60000-60010` — a manual, per-network step, same category as the SSH `2222→22` forward); from a network you don't fully control (a work LAN), the only additional requirement is that network allowing *outbound* UDP, which is out of this repo's hands. Local echo is a **prediction**, not a confirmation — don't trust it as proof a command ran until the connection catches up.

**Remote clipboard (OSC 52) under mosh — fixed 2026-08.** Copying tmux output back to the client machine (copy-mode `y`, or a mouse drag+release, since `mouse on` is already set) works over plain ssh but silently did nothing over mosh: normally tmux relays a copy-mode selection to the terminal emulator as an OSC 52 escape sequence, which the emulator writes to the OS clipboard, but mosh implements its own terminal state machine rather than passing raw escapes through, and its OSC 52 parser only accepts sequences using the CLIPBOARD (`c`) selector — tmux's stock `Ms` capability template doesn't hardcode one, so the sequence was dropped ([mobile-shell/mosh#1054](https://github.com/mobile-shell/mosh/pull/1054), [tmux/tmux#3423](https://github.com/tmux/tmux/issues/3423)). Fixed in `.tmux.conf` with `set -g set-clipboard on` + `set -g allow-passthrough on` + a `terminal-overrides` `Ms` string that hardcodes the `c` selector mosh expects — this is a global tmux fix, not mosh-specific, so it costs nothing over plain ssh either. `allow-passthrough` additionally covers apps inside a pane (vim/nvim, Claude Code) that emit OSC 52 directly rather than going through tmux's own copy-mode. The remaining variable is outside this repo's control: the terminal emulator on the **client** end of the mosh session also has to support *receiving* OSC 52 and writing it to the OS clipboard — true of kitty, Alacritty, foot, WezTerm, and Windows Terminal ≥1.16 (confirmed on the WSL/Windows-Terminal access pattern the tmux/zellij/mosh section is built around — see the Windows Terminal theming section above), false of PuTTY and most corporate SSH clients.

### GTK / Adwaita (`user/gtk/`, `bootstrap/roles/gtk_theme/`)
GTK theming for the unified look (`docs/theming.md`). The hard-won outcome after a deep investigation: **GTK3 apps get dark + the exact `#7c3aed` accent; GTK4/libadwaita apps get dark only** (their accent is locked on Debian's libadwaita — see below). Pieces:
- **The hestia GTK3 theme = recoloured adw-gtk3.** libadwaita-matching GTK3 theme **`adw-gtk3`** (not in Debian apt) is downloaded pinned (`v6.5`, sha256-verified) by the **`gtk_theme` role**, which seds its accent `@define-color accent_bg_color @blue_3` → **`#7c3aed`** and installs it as `~/.local/share/themes/hestia` + `hestia-dark`. No compiler: adw-gtk3 references `@accent_bg_color` at **runtime** (156×), so one `@define-color` edit recolours every accent surface (focus rings, selection, tabs, shaded hovers). Idempotent via a `(version, accent)` marker. This covers GTK3 apps — **Remmina, GIMP, Firefox's file chooser**.
- **The theme's `gtk-4.0/` is stripped by the role — critical.** adw-gtk3 also ships a `gtk-4.0/` (`gtk.css` → `@import libadwaita.css` + `libadwaita-tweaks.css`, a *pinned copy* of libadwaita's own stylesheet). On a mismatched GTK4 those `@`-rules fail to parse (`Theme parser error: … Unknown @ rule`, hundreds of them), so a GTK4/libadwaita app that inherits `GTK_THEME=hestia-dark` loads a **broken** theme and falls back to **light**, ignoring the (correct) dark `color-scheme`. This bit **file-roller's Compress dialog** launched from nemo (light on a dark desktop) — the tell was the `Unknown @ rule` flood when running `file-roller` from a terminal. hestia's GTK4 strategy is **Adwaita + the portal color-scheme** (not adw-gtk3 for GTK4), so the role **removes `~/.local/share/themes/{hestia,hestia-dark}/gtk-4.0`** unconditionally (a no-op once gone, so existing installs are fixed without a rebuild): GTK4 apps then fall through to built-in Adwaita and follow `prefer-dark`, while GTK3 apps keep `gtk-3.0`. The user-level `~/.config/gtk-4.0/gtk.css` (the staged accent, `--accent-bg-color`) is separate and stays. (Even with the broken gtk-4.0 gone, a *set* `GTK_THEME` still forced these apps light — see the next bullet.)
- **Selected by gsettings `gtk-theme` — NOT `GTK_THEME` (corrected 2026-07).** The sway **theme fragment** (`include`d at the top of the config) `exec`s the variant's gsettings at login: **`gtk-theme hestia-dark|hestia`** (in-process GTK3 apps — Remmina, GIMP, nemo, Firefox — *and* the portal file chooser follow this), **`color-scheme prefer-dark|light`** (GTK4/libadwaita + Firefox web content + portal-aware apps), **and `cursor-theme`** — plus a `seat * xcursor_theme` line for sway's own cursor. **`GTK_THEME` is deliberately NOT set.** It was long believed *required* — the note here used to say gsettings/settings.ini are "ignored for the theme name in a non-GNOME sway session." That was a **misdiagnosis**: the launcher's old `GTK_THEME=Adwaita:dark` was *overriding* gsettings and masking it. gsettings themes GTK3 fine on its own (verified live: `env -u GTK_THEME nemo` is dark) — **and a set `GTK_THEME` actively breaks GTK4/libadwaita**, which stops following `color-scheme` and renders light (file-roller's Compress dialog, 2026-07). So `GTK_THEME` was dropped from `start-sway`: GTK3 themes via gsettings, GTK4 via color-scheme, both dark. The **mouse cursor is KDE Breeze** (`breeze-cursor-theme`, apt): white `Breeze_Light` on the dark desktop, standard `breeze_cursors` on light — selected in three places that must stay in sync (the fragment's seat+gsettings, `settings.ini.j2`, and start-sway's `XCURSOR_THEME`/`XCURSOR_SIZE` export for XWayland/Qt/SDL). `gtk-3.0/settings.ini` (**rendered** from a `.j2`, theme name per variant) + the `gtk-3.0/gtk.css` overlay are the belt-and-suspenders that carry the GTK3 theme name alongside gsettings.
- **GTK4 / libadwaita accent — a dead end on trixie, but it's a *version* wait, not a theming dead end.** Proven (three ways, cleanly isolated) that **libadwaita 1.7 locks the accent against user CSS** — neither `@define-color accent_bg_color` nor the `:root { --accent-bg-color }` form recolours gnome-calculator (the file *loads* — a green-window control showed — but the accent doesn't budge), and libadwaita ignores external themes entirely. **The lever is the libadwaita version, not the theme.** libadwaita **≥1.8** moved its colours to GTK CSS custom-properties and accepts an **arbitrary hex** accent (the [styles doc](https://gnome.pages.gitlab.gnome.org/libadwaita/doc/main/styles-and-appearance.html)): `:root { --accent-bg-color: #7c3aed; --accent-color: oklab(from var(--accent-bg-color) var(--standalone-color-oklab)); }`. That's exactly what `gtk-4.0/gtk.css` stages — **inert on 1.7, auto-active at ≥1.8** — so on the move there, gnome-calculator/nautilus get exact `#7c3aed` **from our own CSS, no Ubuntu patch and no Yaru needed**. Versions (Debian tracker, 2026-06): oldstable **1.2.2** (pre-accent — so *older* Debian is strictly worse), trixie **1.7.6** (frozen; stable never major-bumps), testing/forky + sid **1.9.1**. So the wall falls on the upgrade to **Debian 14**, not before — *don't* franken-mix sid's libadwaita onto trixie. **Refinement for when it activates:** make the staged `:root` set **`--accent-color` standalone too**, not just `--accent-bg-color` (per the doc). The portal `accent-color` stays moot (nine-colour named enum; `xdg-desktop-portal-gtk 1.15.3` doesn't export it). Until Debian 14, GTK4/libadwaita apps are **dark with the default blue accent**.
- **Yaru was evaluated (2026-06) and scoped to *icons only*.** Yaru is a maintained GTK+icon suite with a custom-accent SCSS/meson build, but: for **widgets** it's *heavier* than our one-`sed` adw-gtk3 recolour and gives up the exact `#7c3aed`; for the **GTK4 accent** it doesn't help on Debian — Yaru's libadwaita accent rides **Ubuntu's downstream libadwaita patches** (`style-manager-Support-Yaru-accent-colors.patch`, …) that Debian doesn't carry, so it hits the same 1.7 wall (and ≥1.8 makes it unnecessary anyway — see above). Where Yaru *does* win is **icons** (Suru): adw-gtk3 themes none, and icons are **immune to the libadwaita lock** (just files). So the **`yaru_icons` role** (opt-in, `enable_yaru_icons`, default off) installs a custom **`Yaru-hestia`** theme into `~/.local/share/icons` — but as a **prebuilt artifact, not build-on-deploy**: there's **no sed-shortcut** (Yaru ships accented folders as rasterised PNGs, so the accent must be *rendered* via `meson`/`ninja`/`sassc`/inkscape+xvfb — too heavy/fragile per machine). Instead the **`claude` agent builds it once on demand** and publishes `Yaru-hestia-icons.tar.gz` (base `Yaru` + accent overlay, ~27 MB) as a hestia **release** (`yaru-hestia-v3`); the role just **downloads + sha256-verifies + extracts** it (like `localbin`). Full build/maintenance recipe: `bootstrap/roles/yaru_icons/README.md`. Selected via `gtk-icon-theme-name=Yaru-hestia` in both `settings.ini` + a **guarded** sway `gsettings` exec (set only if the theme exists, so a no-role spin falls back cleanly). **Accent gotcha:** Yaru paints the folder front through a ~15% white overlay that lightens the accent, so it must be **pre-compensated to `#6517ea`** — the rendered front then lands on true `#7c3aed` (verified exactly by sampling the 256px `places/folder.png`; violet's channels all clear the overlay floor, unlike the old red whose green floored at ~38). (v3 is the violet rebuild; v2 was hestia red `#d7005f`, and the former Debian-red v1 used `#c60039`.) We ship the **light** flavour and use it even on the dark desktop (Yaru's *dark* variant re-lightens folders to pink; folders are bg-independent, symbolics recolour via GTK). Keep adw-gtk3 for widgets; KDE/Qt stays a separate **Kvantum** track.
- **Firefox & its `firefoxpwa` PWAs follow hestia-dark.** They're GTK3, so the gsettings `gtk-theme=hestia-dark` themes their **chrome, menus, and file chooser** to the violet accent — no `userChrome` needed (the earlier "Firefox is out of reach" worry was just the old `GTK_THEME=Adwaita:dark` bug masking gsettings; each PWA is a `FFPWA-*` GTK3 window and picks it up too). Dark web *content* comes from `color-scheme`; the only conceivable holdout is in-page form controls drawn by Firefox's own engine, which `userContent.css` could address if ever wanted.
- **Deferred (gradual):** base/surface colours toward the exact hestia palette (`#0a0a0a`/`#111111`/…) in the theme; **Kvantum/Breeze** (the Qt/KDE companion); and the libadwaita accent (auto-resolves at Debian 14 / libadwaita ≥1.8). The **custom `#7c3aed` Yaru *icon* flavor** is **done** — opt-in `yaru_icons` role, rebuilt as `yaru-hestia-v3` (folder render verified at exactly `#7c3aed`). Status table in `docs/theming.md`.

### Chromium-family browsers (`chrome`/`edge`/`chromium_x11` roles) — the XWayland gotcha
Google Chrome, Microsoft Edge, and Debian's `chromium` package (`enable_chrome`/`enable_edge`/`enable_headless_browser`, the last default **on**) share the same underlying engine and the same NVIDIA/wlroots bug, root-caused 2026-08-10:

- **Symptom 1 (the original bug):** a visible flash/jitter on `:hover` state changes — hovering a link, hovering a transparent div — reproduced identically in Edge, Chrome, and Chromium.
- **Ruled out first:** GPU rendering. `--disable-gpu`/`--disable-gpu-compositing` alone (confirmed via `edge://gpu` showing hardware acceleration truly off) did **not** stop it — the same lever that fixed `video-compare`'s flicker (the `video_compare` role, above) and Steam's webview flicker does nothing here, so this is a *different* bug despite the visually similar symptom. The `MESA-LOADER: failed to open nvidia-drm: ... Permission denied` noise these browsers print is a **red herring** — a benign, well-documented cosmetic mismatch (NVIDIA's proprietary GBM library doesn't implement the interface Mesa's generic probe expects); the actual file permissions check out fine (verified via `namei -l` — every step 755/644, root:root, no real access problem).
- **Actual cause: Chromium's native-Wayland Ozone backend itself**, not GPU rendering. Modern Chromium auto-selects native Wayland when `XDG_SESSION_TYPE=wayland` is set (which `start-sway` does for every session) — and that backend has its own known flicker/compositing bugs on wlroots, independent of hardware acceleration (see e.g. Ubuntu bug #2055040 "software rendering under Wayland mode"). This is the same *shape* of problem as Steam's native-Wayland client backend (the `steam` role's gotcha, above) — a Chromium-family app's own Wayland integration being unstable on this compositor, not an NVIDIA driver issue per se.
- **Fix, live-confirmed 2026-08-10:** force these browsers through **XWayland** instead — `--ozone-platform=x11`. This alone kills symptom 1. Same shape as the `steam` role's fix: a `~/.local/bin/<binary>` wrapper script (ahead of `/usr/games`-style system paths in `$PATH`, restricted to standard system dirs internally so it resolves the REAL binary rather than recursing into itself) plus a `~/.local/share/applications/<name>.desktop` override for wofi/app-grid launches (which exec `Exec=` directly, not through `$PATH`). Deployed by the `chrome`/`edge` roles (folded into their existing install tasks) and a new dedicated **`chromium_x11`** role (plain `chromium` has no role of its own — it's just an apt package in the `browser` group — so this rides `enable_headless_browser`, chromium's own install toggle).
- **A residual, occasional flicker remains on XWayland — ACCEPTED, not fixed.** Once forced onto XWayland, an intermittent artifact (at times a diagonal tear splitting the window into two triangles; the exact presentation varied) kept surfacing. Two mitigations were tried and BOTH turned out to be **false positives** on a full re-login retest (fresh XWayland spawn, so each var was genuinely live, not a stale session): `XWAYLAND_NO_GLAMOR=1` in `system/sway-session/start-sway.j2` (forces XWayland's own compositing to software — appeared to fix it in an initial spot-check, reverted to a commented-out escape hatch once the retest showed the flicker persisting regardless) and `--disable-gpu-compositing` added to the browsers' wrapper scripts (forces only Chromium's own UI compositing to software, same story — tried, appeared to help, reverted). **Only `--ozone-platform=x11` is a confirmed fix here.** The residual flicker is accepted as a known limitation — same category as Steam's own unfixed CEF webview flicker (above): no permanent fix identified, not worth chasing further without a real upstream driver/compositor fix to lean on.
- **Lesson for the next case in this family:** `WLR_RENDERER=vulkan` (the compositor's own renderer) has never been confirmed to fix *any* of these — video-compare, Steam, and Chrome/Edge/Chromium's main hover flicker were all actually fixed (where they were fixed at all) by getting the **client** off the GPU-accelerated / native-Wayland path, never by changing the compositor's renderer. But that pattern isn't universal either — the residual XWayland flicker above resisted the same "disable GPU somewhere" approach twice. Check the client/XWayland-integration layer first, but don't assume a fix will land just because the previous one in this family did; confirm with a full re-login retest before calling something fixed, not a same-session spot-check.

### Thunderbird (`user/thunderbird/`)
Email client, hestia-accented (verified live on 140.12 ESR, 2026-07). The GTK theme only reaches its **native GTK widgets** (context menus, file chooser); the main window is Gecko-rendered from **three separate variable chains**, all blue by default — traced by extracting the stylesheets from `/usr/lib/thunderbird/omni.ja`:
1. **`--selected-item-color: var(--sidebar-highlight-background-color, AccentColor)`** (messenger's `variables.css`) — selection, primary buttons, focus rings, tabline, spaces toolbar all derive from it. `AccentColor` itself **ignores the GTK3 theme**: Gecko ≥~126 takes it from libadwaita's palette + the GNOME accent enum (`widget.gtk.libadwaita-colors.enabled`, default true) — the Gecko flavour of the libadwaita-1.7 accent wall in the GTK section.
2. **Hardcoded blues that derive from nothing:** `--primary` (`#0a84ff`), `--color-primary-{soft,default,hover,pressed}` (account hub), `--color-text-highlight`, `--button-link-text-color`.
3. **The toolkit design-system token `--color-accent-primary`** (`tokens-brand.css`) — the Settings tab (`about:preferences`) never loads messenger's `variables.css`; its checkboxes/radios paint from the CSS **`accent-color`** property, set from that token. A `userChrome` override can't reach it — about: pages are *content* documents (`userContent.css`).

The fix is three tracked files in `user/thunderbird/`: **GENERATED** `userChrome.css` + `userContent.css` (render.py — **single files carrying both variants via CSS `light-dark()`**, since TB follows the portal color-scheme; the one render.py target that isn't a dark/light pair) and a plain `user.js` pinning `toolkit.legacyUserProfileCustomizations.stylesheets=true` (loads the chrome CSS) + `widget.gtk.libadwaita-colors.enabled=false` (AccentColor back to the GTK3 theme for content selection/scrollbars). **Shadow-DOM gotcha:** `userChrome.css` targets **`*`, not `:root`** — the unified-toolbar tabs are custom elements whose shadow-root stylesheets re-declare the variables on `:host` (a declared value beats one inherited from `:root`); a user-origin `!important` declared **on the host element itself** — which `*` matches — wins across the shadow boundary. **Deployment:** the profile dir name is randomized (`~/.thunderbird/<hash>.<name>`), so these can't ride the fixed-dest `dotfile_links` manifest (they're absent from the Active-symlinks table by design) — the dotfiles role's `thunderbird.yml` **globs** for any profile holding a `prefs.js` and symlinks all three files into each (no-op when TB has never run; fresh install = start TB once, re-run `--tags dotfiles`, restart TB). The `thunderbird` **package** is the opt-in `email` apt group (`enable_thunderbird`, default false, setup.sh asks) — the theming follows TB's *presence*, not the toggle.
