# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository overview

Personal dotfiles for a Debian-based Linux system running the **Sway (Wayland)** desktop. No build system, no tests, no linting — changes take effect by editing the files directly (the active ones are symlinked into `~` / `~/.config`). Reproducing the machine from scratch is driven by an **Ansible bootstrap** (`bootstrap/`, a dozen roles — see *Bootstrap & system reproduction*); the ordered fresh-install runbook is `docs/install-runbook.md`.

There's no test framework, but a **TUI/keybinding config change can still be smoke-tested headlessly** before shipping — drive the real app (vifm, cmus, imv…) through a **pseudo-tty**, send keystrokes, and scrape the screen to confirm a bind/command actually fires (this is how the vifm `:gc`/`:gd`/`:gr`/`:gh` helpers were verified). Sketch: Python `pty.fork()` → child `execvp`s the app, parent sets the window size via `TIOCSWINSZ` (else no preview pane renders), points the app at a scratch config (vifm: the `VIFM` env var, **not** `--config-dir`), then writes keys and strips ANSI from the read buffer. Watch the gotchas: a `:command` must be sent with its leading colon (bare `gc` types normal-mode `g`,`c`); `:!pwd` reports the process cwd, not the browsing dir (scrape the header instead); and clean up strays by exact PID, not `pkill -f vifm` (which also matches the driver's own shell).

The repo is growing from *one person's dotfiles* toward a **reproducible Debian spin** with multiple principals and `/etc` system configs; the target layered structure is `docs/repo-structure-design.md` (phased, not yet migrated).

The configs are converging on one unified theme: dark ground `#1a1a1a` (lifted from near-black `#0a0a0a` in 2026-07, palette 0.5.0), accent **violet `#7c3aed`** (thecodingidiot's brand accent, adopted 0.10.0; the retired accent red `#d7005f`, retuned to a true red **`#d70000`** (0.10.1), lives on as the **`danger`** role — error / critical / destructive-confirm / wrong-password — and as ANSI color01), and a saturated 16-colour + code-syntax palette **re-anchored on thecodingidiot's Memphis brand** (0.9.x–0.10.0; was wildcharm red `#d7005f`, and Debian red `#ce0056` before 2026-06). Vim/Neovim use the **`hestia`** colorscheme (`user/vim/colors/hestia.vim`) — since 2026-07 a self-contained scheme **GENERATED by `render.py`** from `palette.yml` (a thin wrapper over built-in `wildcharm` until then); inspired by `wildcharm` (the palette was derived from it) but now owned by hestia and identical in Vim and Neovim. The palette is now defined once in **`themes/hestia/palette.yml`** (the single source of truth — semantic roles, the 16 ANSI colours, and a versioned **`syntax:`** role table for code highlighting re-anchored on the tci Memphis brand — plus a `danger` role and per-file-type icon colours), and the **per-app theming process** (+ a themed/not-yet status table) is **`docs/theming.md`**. Keep new theming consistent with this — and when theming an app, follow that process. Since M7 (palette 0.6.0) the desktop can also run the **light variant** — ground `#f5f5f5`, same accent — switched by the bootstrap's **`theme_variant: dark|light`** (host_vars; setup.sh asks; flip = re-run `--tags dotfiles,sway_session` + **re-login**); the dark/light system and cross-platform syntax coherence (vim / bat / Shiki / VS Code) — layer model, decision log, milestones, inconsistency backlog — are governed by **`docs/theme-roadmap.md`**; syntax consumers render from the `syntax:` table, never ad hoc. The TextMate-family artifacts (bat's `.tmTheme`, the web Shiki pair in `themes/hestia/dist/shiki/`, the VS Code themes in `user/vscode/hestia/`) **and the per-app colour files** (the `user/{kitty,sway,mako,tmux}/theme-{dark,light}.conf` and `user/alacritty/theme-{dark,light}.toml`, `user/{waybar,wofi}/theme-{dark,light}.css` and `user/zathura/theme-{dark,light}` fragments included/`@import`ed by the main configs; the `user/{swaylock,swaynag}/config-{dark,light}` whole-file pairs; and the `user/vifm/colors/hestia-*.vifm` / `user/bat/themes/hestia-*.tmTheme` / `user/glow/hestia-*.json` / `user/zellij/hestia-*.kdl` theme pairs — in every case the `theme_variant` one is symlinked to a variant-neutral dest — plus the single-file `user/thunderbird/user{Chrome,Content}.css`, which carry BOTH variants in one file via CSS `light-dark()`, no pair/symlink; and the Vim/Neovim colorscheme `user/vim/colors/hestia.vim`, one symlinked file carrying both `&background` branches) are **GENERATED** by **`themes/hestia/render.py`** from `palette.yml` + **`scopes.yml`** (the shared role→scope map) — never hand-edit them; edit the sources, re-render (`render.py`), and use `render.py --check` to detect drift.

## Running as the `claude` agent user

Claude Code runs here as a dedicated, unprivileged **`claude`** Linux user (own `0700` home `/home/claude`, member of the **`devshare`** group, **not** in sudo) — a kernel-enforced trust boundary, not a behavioural one. Full design: `docs/claude-user-design.md` (implemented 2026-06-20); day-to-day workflow: `docs/working-with-claude.md`. What matters when working in this repo:

- **This checkout (`/srv/devshare/hestia`) is claude's own clone** in the shared `/srv/devshare` tree — claude's *workspace*, **not** the live system. The dotfiles are symlinked from **dimitrios's** clone at **`~/Development/hestia`**, which is the deployment source. Edits made here reach the running system only when **dimitrios pulls** after reviewing a pushed branch — so an edit here is **not** live. Never treat `/srv/devshare/hestia` as the deployment source. (No `/home/dimitrios/...` literals remain in any deployed config — every host-specific path resolves from `target_home`/`repo_root`/`$HOME`/host_vars at deploy time. Path generalisation is **complete**, `docs/repo-structure-design.md` §5.)
- **Collaboration is git-mediated, two principals.** claude commits and signs as **itself**, pushes a topic branch, and opens a **pull request** as the GitHub bot **`dimitrios-claude`** (`gh pr create`; commits show **Verified**); dimitrios reviews, **merge-commits** (preserves the signed commits; via `gh pr merge --admin`), and pulls to deploy. claude **never** self-merges — and *cannot*: a `main` ruleset (*Restrict updates*, admin-only bypass) blocks the agent from pushing to or merging `main` server-side, so its only route is opening a PR. The concrete loop (and the `gh`/PAT auth) is in `docs/working-with-claude.md`.
- **claude's identity:** own SSH key `~/.ssh/id_claude`, own **passwordless** GPG key `4AA9DD310356AD0E`, git author `Claude (dimitrios's agent) <claude@charalampidis.pro>`.
- **Signing is frictionless for claude** — the passwordless key needs **no pinentry, no agent cache, no `gpg-unlock`, and not `gpg-wrapper.sh`**. All that machinery in *Secrets & commit signing* below is **dimitrios's**; it does not apply when running as claude.
- **Isolation:** claude **cannot** read dimitrios's home, `~/.ssh`, `~/.gnupg`, or `~/.bash_secrets` (different UID; `0750`/`0700`/`0600`). Confirm any time: `ls ~dimitrios` → Permission denied.
- **`user/bin/claude-access`** (`grant|revoke|list`, symlinked to `~/.local/bin/`) is the escape hatch to give claude ACL access to a path **outside** `/srv/devshare` (e.g. a project in the human's home), with a tracked registry. Prefer the clone-and-sync model; reach for it only when in-place editing is truly needed.
- **claude can install its own user-level tooling.** Because `claude` is a separate user with its own `/home/claude`, it can freely install whatever a task needs **into its own home** — npm/pip `--user`, cargo, a downloaded binary into `~/.local/bin`, etc. — without `sudo` and without touching dimitrios's environment. (System-wide `apt` installs still need the human; those stay dimitrios's job.)
- **claude's terminal environment is deployed from the same sources** (the *claude-environment-parity* pass — `docs/claude-env-parity-design.md`). A **second `dotfiles` run** in `site.yml` deploys the manifest subset tagged **`claude: true`** (terminal + theme + Claude Code config) into `claude`'s home, symlinked from **claude's own clone** (`/srv/devshare/hestia`, so its env tracks the branch under review), `become`-ing claude only when the runner isn't already claude. It reuses the same role via the `dotfiles_links`/`dotfiles_templated` indirection (default = the full manifest; the claude play overrides them with the `claude_dotfile_links`/`claude_templated_configs` slices). **Never** deployed to claude: identity/secrets/privileged configs (gitconfig, credential scripts, keys, `.bash_secrets`) — those stay claude's own (the `claude_user` role). Run it standalone with `--tags claude_env`.
- **claude can shoot themed screenshots headlessly** — the *Tier-B screenshot rig* **`user/bin/hestia-shot`** (deployed to claude's `~/.local/bin`). It spins up a throwaway **nested sway** on the wlroots **headless** backend (`WLR_BACKENDS=headless` + `WLR_RENDERER=pixman` — no GPU/DRM/seat), wrapped in `dbus-run-session` (so **waybar** maps), paints the hestia theme + a mesh-PNG wallpaper (`output bg`, from claude's deployed `~/.local/share/backgrounds/hestia`), runs the scene, `grim`s it, and tears the tree down cleanly (`setsid` group + `swaymsg exit`). Scenes: `desktop` (waybar + wallpaper + tiled vifm — the full composite), `vifm`/`ranger`/`yazi`, or `app "<cmd>"`. Reads its configs from claude's clone, so a shot reflects the branch under review. The **`enable_claude_rig`** pass (site.yml, rides `enable_claude_user`) gives claude the rig's desktop tools/assets — `wpaperd`/`awww` (localbin) + the mesh wallpapers — so composites use the real deployed background (`--tags claude_rig`). This is how the showcase images are re-shot without a live desktop (`docs/claude-env-parity-design.md` §7).

## File layout and naming convention

Top level: **`user/`** (the human's home-deployed configs — one subdir per tool), **`system/`** (root-owned `/etc` configs), **`bootstrap/`** (the Ansible installer), **`themes/`** (the theme single-source-of-truth — `hestia/palette.yml`; see *Theming* / `docs/theming.md`), **`docs/`** (maintainer design docs/runbooks), **`showcase/`** (READER-facing docs: per-category evaluation-trace chapters + screenshots — index `showcase/README.md`; each concluded evaluation ships its chapter in/beside the verdict PR; plain markdown + relative `img/` paths so chapters syndicate to the stoa charalampidis app unchanged). The `user/` grouping is a flat namespace — *not* `users/<name>/`: per-user values are parameterised (host_vars/templating, §6), so a username sub-level would be empty ceremony (see `docs/repo-structure-design.md` §7).

Active `user/` configs are either:
- **Dot-prefixed** in the repo, symlinked into `$HOME` — `user/vim/.vimrc` → `~/.vimrc`, `user/bash/.bashrc` → `~/.bashrc`, `user/git/.gitignore_global` → `~/.gitignore_global`.
- **Plain files under the app dir**, symlinked into `~/.config/<app>/` — sway, waybar, mako, wofi, cava, cmus, alacritty, kitty, imv, vifm, glow (`hestia.json`), nvim, xdg-desktop-portal.
- **Rendered (not symlinked)** — a small **path-generalised / identity-bearing** set rendered from `.j2` by the bootstrap (`user/git/.gitconfig`, `user/glow/glow.yml`, `user/cmus/rc`, and the two credential scripts `credential-unlock.sh` + `keyring-ssh-askpass.sh`); see *Rendered (templated) configs* below.
- **`user/bin/`** — small helper scripts symlinked into `~/.local/bin/` (currently `claude-access`; see *Running as the `claude` agent user*).
- **`system/`** — layer-(a) **system configs** deployed by **copy**/template to root-owned locations (**not** symlinked), driven by Ansible roles: `system/samba/smb.conf` → `/etc/` (`samba` role); `system/sway-session/{start-sway → /usr/local/bin/, greetd-config.toml → /etc/greetd/config.toml}` (`sway_session` role); `system/docker/<app>/` → `/opt/<app>/` (`docker_services` role — the container layer). Each `system/` subdir keeps a `README.md` runbook.
- **`bootstrap/`**, **`docs/`** — the Ansible installer + the design docs/runbooks (cross-cutting, not a per-tool config).

Two `/srv` trees live outside the repo but are part of the setup: **`/srv/devshare`** (the human↔`claude` shared dev tree — group `devshare`, setgid + default ACLs; this clone lives here) and **`/srv/smbshare`** (the Samba share — group `smbshare`; `docs/file-sharing-design.md`).

## Secrets & commit signing

> This section describes **dimitrios's** interactive setup (the passphrase-protected key + the pinentry-wedge machinery built around it). When running as the **`claude`** user, signing is **passwordless** and none of the wrapper / cache / `gpg-unlock` flow applies — see *Running as the `claude` agent user*.

- **Secrets** (API tokens, etc.) live in **`~/.bash_secrets`** — untracked, mode 600, sourced at the end of `user/bash/.bashrc`. Never commit secret values; a bootstrap script must not carry this file.
- **Commits are GPG-signed** (the signing key id is an **installer input** — `git_signingkey` in host_vars, rendered into both `user/git/.gitconfig.j2` and `credential-unlock.sh`; empty → `gpgsign = false`). Signing is routed through **`user/git/gpg-wrapper.sh`** (set as `gpg.program` in `user/git/.gitconfig.j2`, templated from `{{ repo_root }}` so it follows the clone — no manual update on move). In a normal terminal it execs `gpg` untouched, using **`pinentry-tty`** (configured in **`user/gnupg/gpg-agent.conf`**, symlinked to `~/.gnupg/`) with a **~session-length cache TTL** (`34560000`) — because login auto-unlock (below) warms the agent at login, so the security boundary is the unlocked session + screen lock, not the TTL; GPG now matches ssh-agent's persist-until-logout.
- **Why the wrapper:** inside Claude Code (`$CLAUDECODE` set) gpg-agent would launch pinentry on `GPG_TTY` — which is Claude's own terminal (`/dev/pts/0`), **not** the calling process's stdin — and **seize it** (you can't type the passphrase or control the prompt; `pinentry-tty` does *not* avoid this, the tty takeover is the problem). So under `$CLAUDECODE` the wrapper adds `--pinentry-mode error`: a **warm** cache signs silently, a **cold** cache fails fast (`gpg: signing failed: No pinentry`, exit 2) instead of wedging. When a harness commit fails this way, run **`gpg-unlock`** (a `user/bash/.bashrc` function — signs a throwaway message so gpg-agent prompts once via pinentry-tty; reads the key from git config, so no hash to remember; refuses to run under `$CLAUDECODE`) in a normal terminal, then the harness can sign again within the cache window.
- **Bootstrap / pinentry default:** the tracked `gpg-agent.conf` forces `pinentry-tty` per-agent, but the *system* `pinentry` alternative defaults to **`pinentry-curses`** (leaks mouse-tracking escape codes). Pin it belt-and-suspenders with `sudo update-alternatives --set pinentry /usr/bin/pinentry-tty`. Avoid `pinentry-curses` and `pinentry-gnome3` (the latter falls back to curses outside GNOME).
- **Login auto-unlock (SSH + GPG):** `pam_gnome_keyring` unlocks the gnome-keyring login keyring at login; the Sway-`exec` hook **`user/gnupg/credential-unlock.sh`** then loads the SSH key (via an SSH_ASKPASS helper reading the keyring) and warms gpg-agent (loopback sign), so **no per-boot `ssh-add`/`gpg-unlock`** — including for the harness. Passphrases live in the keyring (`secret-tool store … autounlock ssh/gpg …`). Full story incl. the gnome-keyring launcher-untangle needed to make PAM the sole unlocker: `docs/credential-autounlock-design.md` §10. The wrapper + `gpg-unlock` remain as fail-clean fallbacks for a cold cache.

## Bootstrap & system reproduction (`bootstrap/`)

A fresh machine is reproduced by an **Ansible** playbook (engine decision: `docs/repo-structure-design.md`). The one-shot entry point is **`bootstrap/setup.sh`** — installs Ansible, interactively gathers host answers (the §6 feature toggles + `samba_lan_subnet` + `cmus_music_dir` + `theme_variant` dark|light, with auto-detected defaults) into the untracked `host_vars/localhost.yml`, then runs the playbook (re-runnable; own flags `--no-backup`/`--yes`/`-h`/`--help`, everything else passes through — and `--check` is a true dry-run: answers go to a temp file, real `host_vars` untouched, ansible only previews). It **captures the sudo password up front with its own retry loop** (validating each attempt via `sudo -S -v`, 3 tries) and hands it to ansible via `--become-password-file` pointing at a **tmpfs file** (`$XDG_RUNTIME_DIR`/`/dev/shm` — RAM-backed, `0600`, removed right after the run), instead of ansible's single-shot `--ask-become-pass` where one typo aborts the whole play. (Two things that *don't* work, learned the hard way: a cached `sudo -v` timestamp — sudo's `tty_tickets` keys it to the shell's tty but ansible's become runs on a different tty; and process-substitution `<(…)` for the password file — ansible re-opens the path by name and `/dev/fd/N` resolves to an unopenable `pipe:[inode]`.) The NOPASSWD probe runs `sudo -k` first so a warm cache can't masquerade as passwordless. **`--yes`/`-y`** skips the questionnaire and reuses the saved `host_vars` as-is (resume a failed run). **It is destructive on a fresh `$HOME`** (the `dotfiles` role force-replaces existing dotfiles) — so a *first run* (no host_vars yet) shows a ⚠️ replace notice (in dry-run too — it's a simulation) and on a real apply requires typing `yes`, and **on the first deploy only** (marker-tracked at `~/.local/state/hestia/.dotfiles-backed-up`) the role copies any pre-existing real config to `<file>.bak` next to it — one `.bak` per file, ever, no accumulation. Disable with `--no-backup` (= `-e dotfiles_backup=false`); then replaced configs aren't saved. The ordered start-to-finish narrative — which role when, with the interactive/external manual steps interleaved — is **`docs/install-runbook.md`**; the per-role reference is `bootstrap/README.md`.

- **Single source of truth: `bootstrap/group_vars/all.yml`** — the manifest listing every dotfile symlink (`dotfile_links`) and the apt package set (`apt_packages`). The "Active symlinks" table above is **generated** from it by `bootstrap/gen-symlink-table.py`; run that after editing `dotfile_links` rather than hand-editing the table.
- **Per-host personal values** (e.g. the Samba `samba_lan_subnet`) live in an **untracked** `bootstrap/host_vars/<inventory_host>.yml` (template: the committed `…example`), kept out of this public repo by `.gitignore`. Ansible auto-loads it; role defaults carry RFC 5737 placeholders so a checkout is runnable without it.
- **Roles** (`bootstrap/site.yml`, sliceable by `--tags`): `packages` (apt — and, after install, it disables iperf3's bundled server daemon: iperf3 ships as a client-side throughput diagnostic, but its `iperf3.service` would otherwise listen on tcp/5201, so the role keeps the unit disabled+stopped), `dotfiles` (symlink the manifest + render `templated_configs` into `$HOME`, no root), `fonts` (the Nerd Fonts the configs reference — `Lilex`/`BigBlueTermPlus` — fetched from the pinned nerd-fonts release into `~/.local/share/fonts`, no root), `tailscale` (installs the Tailscale mesh VPN from its own signed apt repo — the share's transport + general remote reach; amd64-only, self-skips elsewhere; `steam-installer` is itself a thin bootstrap wrapper — the real Valve client download + sign-in happens on first `steam` launch and stays manual/GUI, like MEGAsync's. **Gotcha (Steam's "missing 32-bit libGL.so.1" warning):** `glx-alternative-mesa`/`glx-alternative-nvidia` (mesa's and, on an NVIDIA host, the proprietary driver's GLX-vendor selectors) are `Multi-Arch: foreign` singletons whose postinst registers an `update-alternatives --slave` link **per architecture found installed at that CONFIGURE time** — since i386 didn't exist yet when they last ran (before this role added it), neither ever created an i386 slave, so `/usr/lib/i386-linux-gnu/libGL.so.1` stays diverted-away with nothing filling it back in, even after `steam-libs:i386` pulls Mesa's i386 GL. The role's fix: gather `package_facts`, and when `glx-alternative-nvidia` is installed also apt-install `nvidia-driver-libs:i386` (a Recommends of the amd64 `nvidia-driver-libs` that was never resolvable before i386 existed — gives 32-bit apps real NVIDIA-accelerated GL instead of a Mesa/llvmpipe software fallback), then — only if `/usr/lib/i386-linux-gnu/libGL.so.1` still doesn't exist — `dpkg-reconfigure` `glx-alternative-mesa` (always) and `glx-alternative-nvidia` (if present, last, so it keeps the active/highest-priority slot matching the already-selected 64-bit provider) to force both to re-scan and register the now-available i386 libraries. Installing `nvidia-alternative:i386`/`glx-alternative-mesa:i386` directly (the naive fix) is a trap: both are `Multi-Arch: foreign`, so apt resolves the `:i386` build by **removing the working amd64 one** — verified live via `apt-get install --simulate` before landing on the `dpkg-reconfigure`-the-amd64-copy approach instead. **Gotcha (Steam's UI flicker + a sway CRASH on NVIDIA/Wayland):** Steam's client UI (steamwebhelper) is Chromium/CEF, and its native-Wayland windowing backend is unstable on wlroots — on an NVIDIA host it corrupted XWayland override-redirect surfaces (the File menu rendered broken, the cursor tore) and, worse, **crashed sway outright** resizing a tiled window next to it, dropping the session back to the login manager. The compositor-wide `WLR_RENDERER=vulkan` mitigation (see the Sway section) was tried first — it's the interim fix for the general NVIDIA implicit-sync flicker (Edge, VSCode, and — confirmed 2026-08 — any GL-accelerated Wayland client, e.g. video-compare's SDL2 renderer) — but made Steam's XWayland corruption *worse* and was **reverted** as a first pass (`system/sway-session/start-sway.j2`, 2026-08). It was then **re-enabled** (2026-08) to fix the video-compare flicker, re-testing the Steam interaction now that Steam has its own XWayland-forcing fix (below) for a separate crash bug — if Steam regresses again under Vulkan, re-comment `WLR_RENDERER=vulkan` and re-login; that was the original deciding factor. For Steam specifically, the role also forces it through **XWayland** (`XDG_SESSION_TYPE=x11`, scoped to just that process — sidesteps Steam's buggy native backend rather than fighting the compositor renderer over it) via two deployed overrides: a `~/.local/bin/steam` wrapper script (ahead of `/usr/games` in `$PATH`, so a plain `steam` in a terminal picks it up, and it execs the real Debian launcher untouched so it survives Steam's own self-updates) and a `~/.local/share/applications/steam.desktop` override (same fix for wofi/app-grid launches, which exec `Exec=` directly rather than going through `$PATH`; user-level XDG paths take precedence over steam-installer's system one — though if the real Valve client ever re-registers its own desktop entry at that same user path, it silently clobbers the override, unaffecting the terminal wrapper; re-run `--tags steam` to reassert it). XWayland alone fixed the menu/cursor corruption and the crash; a **separate, remaining flicker** in Steam's own storefront/library web views is a distinct, well-documented upstream NVIDIA+Wayland+CEF bug (confirmed on this exact 550.163 driver via the [NVIDIA developer forums](https://forums.developer.nvidia.com/t/550-wayland-steam-has-glitches-when-launched-with-gpu-accelerated-rendering/290157)) with no permanent fix — only Steam's own **Settings > Interface > "Enable GPU accelerated rendering in web views"** toggle (disable it) works around it, at the cost of a less snappy Store/Library UI; actual game rendering is unaffected since games don't go through CEF; **UPDATE 2026-08-10:** `WLR_RENDERER=vulkan` has since turned out to never have been confirmed to fix any of this — see the Chromium-family browsers section below for the full corrected story), `samba` (layer-(a) `/etc/samba/smb.conf` + `/srv/smbshare` share — its `hosts allow` adds the Tailscale CGNAT range only when `enable_tailscale` is also on, otherwise LAN-only), `claude_user` (the `claude` user + `devshare` group + shared trees + repo ACLs — the *plumbing* — **plus claude's local identity**: passwordless SSH/GPG keys + `~/.ssh/config` + git config via `tasks/identity.yml` (rendered from a template, run as claude via `sudo -H -u claude` from root to dodge the unprivileged-become temp-file gotcha; GPG gated by `claude_sign_commits`), and it **prints** the irreducibly-manual GitHub steps — bot account, key uploads, PAT, repo-invite command — at the end), `credentials` (gnome-keyring launcher-untangle for login auto-unlock). There's also **`localbin`** — pinned prebuilt binaries from GitHub releases into `~/.local/bin` (no root), data-driven via `localbin_binaries` (**bluetuith**, **hcloud** the Hetzner Cloud CLI, and **tofu**/OpenTofu for Cloudflare-DNS-as-code, and **cf-terraforming** to export existing Cloudflare config into `.tf`, plus the toggle-gated **yazi**/**ya** pair of the file-manager evaluation and the **wpaperd/wpaperctl/awww/awww-daemon** wallpaper-evaluation set (`enable_wallpapers`; Each role is idempotent — re-run with `--check` to verify `changed=0`. **`packages` + `dotfiles` + `fonts` + `localbin` + `gtk_theme` + `sway_session` are core; samba/tailscale/firefoxpwa/claude_user/credentials are optional**, gated by `enable_samba`/`enable_tailscale`/`enable_firefoxpwa`/`enable_claude_user`/`enable_credentials` (`group_vars/all.yml`, default `true`) via `when: … | bool` — the §6 feature-flag surface; set one false (host_vars or `-e enable_samba=false`) to skip its role. `yaru_icons` (`enable_yaru_icons`), `nvidia` (`enable_nvidia`), `razer` (`enable_razer`), `openrgb` (`enable_openrgb`), `chrome` (`enable_chrome`), `trading` (`enable_trading`), `mega` (`enable_mega`), `steam` (`enable_steam`), `video_compare` (`enable_video_compare` — builds [pixop/video-compare](https://github.com/pixop/video-compare) from source into `~/.local/bin`: no apt package and upstream's GitHub releases are Windows-only zips, so it's the same build-from-source shape as the FFmpeg/SDL2 dev-headers apt group it rides (`video_compare` in `package_group_features`); pinned to a date tag, `bootstrap/roles/video_compare/README.md`. **Gotcha (NVIDIA/Wayland flicker):** video-compare's default GPU-accelerated SDL2 renderer hits an NVIDIA-550 Wayland texture-streaming race, live-confirmed on hephaestus (2026-08) as a flash of background colour at the seam between the left/right panes on mouse motion, in every display mode — NOT fixed by `-W`/`--window-fit-display` or by the compositor-wide `WLR_RENDERER=vulkan` mitigation (a separate sync domain from video-compare's own SDL2 GL context). - **Personalization seam** (`docs/personalizing.md`): three layers for making hestia someone else's system without editing role/playbook logic — (1) override values/lists in **host_vars** (toggles, plus wholesale `apt_packages:`/`nerd_fonts:`/`localbin_binaries:` overrides), (2) install anything custom via an untracked **`bootstrap/local.yml`** Ansible *tasks* file (gitignored; committed `local.yml.example`; `site.yml`'s final play `include_tasks` it **last** if present, `tag: local`; `become:` tasks reuse setup.sh's sudo password), (3) fork the `user/` configs. Goal 1 stays the tracked default; nobody edits `bootstrap/roles/` or `site.yml` to personalize. (Chosen over per-role `extra_*` vars, which don't scale.)
- **Samba share** (`system/samba/smb.conf.j2`, `docs/file-sharing-design.md`): SMB to a Windows laptop, POSIX-ACL permission model. The `samba` role **renders** the template (LAN subnet from host_vars) → `/etc/samba/smb.conf`. smbd listens on all interfaces; access is confined at the SMB layer by `hosts allow/deny` (loopback + home LAN, **+ the Tailscale CGNAT range when `enable_tailscale` is on** — the template gates that line and its Tailscale-flavoured comments on the toggle, so a Tailscale-less spin renders a clean LAN-only config) + SMB3 floor + a `nologin` `smbshare` principal.

- **Container layer** (`system/docker/`, runbook `system/docker/README.md`): the Docker Compose stacks that make this host a media/photo server — **Plex**, **Stash**, **Immich** (+ a **Caddy** TLS front end) — rendered from `system/docker/<app>/*.j2` to **`/opt/<app>/`**, the same layer-(a) copy/template shape as samba (`/opt` is where this host has always kept container apps, alongside the vendor installs that put themselves there). Two roles: **`docker`** (Engine + Compose v2 from **Debian's own** apt — `docker.io`/`docker-cli`/`docker-compose`/`containerd`, no vendor repo or keyring, unlike tailscale/mega/chrome — plus `docker` group membership and the daemon) and **`docker_services`** (renders each enabled stack, creates its host data dirs, then `docker compose up -d`). Adding a service is a **`docker_services` manifest entry + a template dir**; no role code changes. Everything is gated by `enable_docker` + per-stack `enable_plex`/`enable_stash`/`enable_immich`, all **default `false`** — this is server-shaped, not part of a workstation spin. **Secrets** (`immich_db_password`, `plex_claim`, `duckdns_token`) live in **gitignored host_vars** and are rendered at deploy time — the repo is public, so no literal credential may sit in a template; `.env` renders `0600` and the role **asserts** the required ones are non-empty rather than deploying a broken stack. `setup.sh` **preserves** an existing `immich_db_password` and only generates one on a fresh setup (a new password against an existing Postgres volume would lock Immich out of its own database). Note the `docker` group is effectively **root-equivalent** (a member can bind-mount `/` into a container), which is why the **`claude` agent user is deliberately excluded** — it has no sudo either, so the container layer stays dimitrios's. Manual by design (same rationale as `smbpasswd`/`tailscale up`): the Plex claim, the Immich admin account, enabling NVENC in the Immich UI, adding the External Library, and the router's 80/443 forwards. A companion **`duckdns`** role (no root, `enable_duckdns`) renders the token config `0600` + a cron entry and ships `user/bin/duckdns-update` via the dotfiles manifest — it supplies the **hostname TLS needs**, since Let's Encrypt will not certify a bare IP even on a static-IP host.

- **Remote access — sshd hardening + fail2ban** (`system/ssh/`, `system/fail2ban/`; runbook `system/ssh/README.md`): keys-only sshd with **no root login** and an optional **TOTP second factor**, deployed as a layer-(a) **drop-in** at `/etc/ssh/sshd_config.d/10-hestia.conf` — never an edit to Debian's `sshd_config`, which has `Include …sshd_config.d/*.conf` on its first line and takes the FIRST value for most keywords, so an early-sorting drop-in wins and survives package upgrades. Two roles, both **default off**: **`ssh_server`** and **`fail2ban`**. The whole design is shaped by the **lockout problem** — disabling password auth before a key works is the one mistake here that is hard to undo — so: the role installs `~/.ssh/{{ ssh_key_file }}.pub` into `authorized_keys` then **re-reads it and refuses to continue if still empty**; TOTP is gated on `~/.google_authenticator` already existing (else sshd would demand a code the user cannot produce); the handler **reloads** rather than restarts (established sessions survive a bad config); and the config deploy is a **block/rescue that removes its own drop-in** if the merged `sshd -t` fails. Note `validate:` on the template is unusable here — `sshd -t -f <dropin>` exits "no hostkeys available", since only the MERGED config is meaningful. **TOTP is internet-only**: a `Match Address` block exempts the LAN + Tailscale CGNAT range (`ssh_trusted_networks`), because a 6-digit code in front of every scp/rsync/git-over-ssh from inside the house buys nothing against the actual threat model. The PAM side matters — Debian's `/etc/pam.d/sshd` includes `common-auth`, which would prompt for the **Unix password** at the keyboard-interactive stage and defeat "keys only"; the role comments it out and requires `pam_google_authenticator.so` **without `nullok`** (unenrolled = denied, not waved through). Manual by design: the interactive `google-authenticator` enrolment (its secret + scratch codes must never touch the repo) and the router's external-2222 → internal-22 forward — a non-standard external port is a **log-noise** measure, not a security one. fail2ban renders `/etc/fail2ban/jail.local` (never `jail.conf`, which upgrades replace) with **`backend = systemd`** — mandatory on Debian 12+, where sshd logs to the journal and the default `auto` backend can silently watch a file that never updates — plus `ignoreip` for LAN/tailnet and a `recidive` jail. Be clear on what it buys: against key-only sshd it stops almost nothing that could have succeeded; **key-only auth is the boundary, fail2ban makes the evidence readable**.
